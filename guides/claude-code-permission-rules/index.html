Claude Code の権限ルールの書き方:Bash・Read のパターンと allow・deny の優先順位

公開: 2026年10月24日 ・ 中小DXラボ ・ 内容は執筆時点(2026年10月)の公式ドキュメントなどの出典にもとづきます(各節の末尾に出典を記載)

結論

  • 権限ルールは Tool か Tool(specifier) の形で書きます。ツール名だけなら全件、括弧で指定子を付けると絞り込めます。
  • Bash の * はサブコマンドの後ろに置きます。Bash(git log *) は git log だけ、Bash(git *) は git の全コマンドに一致します。
  • deny はどの階層でも allow に勝ちます。プロジェクトの allow は、ワークスペースの信頼ダイアログを承認するまで適用されません。

権限ルールの基本形:ツール名と指定子

執筆時点(2026年10月)の公式ドキュメントによると、権限ルールは Tool または Tool(specifier) の形式で書きます。指定子の中の括弧は文字としてそのまま扱われるため、括弧を含むコマンドやパスでもエスケープは不要です。Claude Code(Anthropic 社が提供する、ターミナルで動く AI コーディングエージェント)の許可・拒否の対象を、この書式で指定します。

ツール全体と、指定子での絞り込み

  • Bash、WebFetch、Read のようにツール名だけを書くと、それぞれすべての Bash コマンド、すべての Web 取得リクエスト、すべてのファイル読み取りに一致します
  • Bash(npm run build) は npm run build というコマンドそのものに一致します
  • Read(./.env) はカレントディレクトリの .env ファイルの読み取りに一致します
  • WebFetch(domain:example.com) は example.com への取得リクエストに一致します

Bash(*) は Bash と同じ意味です。deny ルールの場合、どちらの形でもそのツールは Claude のコンテキストから外れます。また、ツールの表示ラベルと正式名は異なることがあり(例:Stop Task の正式名は TaskStop)、ルールは表示ラベルには一致しません。正式名は公式のツールリファレンスで確認してください。

出典: Configure permissions

Bash ルールのワイルドカード:* の置き場所が肝心

Bash ルールの * は空白を含む任意の文字列に一致し、* を含まないルールは1つのコマンドそのものに一致します。公式ドキュメントは、* をサブコマンドの後ろに置くよう警告しています。最初の * より前は書いたとおりに照合されるため、Bash(git log *) は git log だけ、Bash(git *) は git のすべてのコマンドを許可します。Bash(git * main) のようにサブコマンドの前に * を置いた allow ルールは、起動時に警告されます。

次の設定では、npm のスクリプトと git commit は確認なしで実行され、git push で始まるコマンドは拒否されます。ただし git -C . push のような別の書き方の push は一致しません。詳細は公式ドキュメントで確認してください。

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}

一致の例

  • Bash(npm run *) は npm run build や npm run に一致し、npm install には一致しません
  • Bash(ls *) は ls -la と ls に一致し、lsof には一致しません。Bash(ls*) は lsof にも一致します
  • Bash(* --help *) は npm --help x に一致しますが、npm --help には一致しません

末尾の空白付き * が素のコマンドにも一致するのは、その * がルール内で唯一のワイルドカードの場合だけです。また、末尾の * の前の空白はルールの一部です。:* は末尾ワイルドカードの同等の書き方で、Bash(ls:*) は Bash(ls *) と同じ意味ですが、パターンの末尾でのみ認識されます。Bash(git:* push) ではコロンが文字そのものとして扱われ、git コマンドには一致しません。

パラメータ指定とツール名ワイルドカード

deny と ask のルールは、組み込みツールのトップレベルの入力パラメータに Tool(param:value) で一致できます。allow ルールは、これまでどおり各ツール自身の指定子の構文を使います。

  • Agent(model:opus) は Opus モデル階層を要求する Agent 呼び出しに一致します
  • Bash(run_in_background:true) はバックグラウンドで動く Bash 呼び出しに一致します
  • 1つのルールで指定できるパラメータは1つです。複数を条件にしたい場合はルールを2つ書きます
  • 値の * は任意の文字列に一致し、* が無ければ完全一致です

Bash の command や Read の file_path のような主要な内容フィールドは、この方法では指定できません。Bash(command:rm *) は複合コマンドで回避され得るため、Claude Code は無視して起動時に警告します。代わりに Bash(rm *)、Read(./path)、WebFetch(domain:host) を使ってください。

deny と ask のルールは、ツール名の位置にも glob パターンを使えます。"*" は全ツール、"mcp__*" は全サーバーの MCP ツールに一致します。次の設定はすべての MCP ツールを拒否します。

{
  "permissions": {
    "deny": [
      "mcp__*"
    ]
  }
}

allow ルールは、リテラルの mcp__ とサーバー名の後ろにだけ glob を置けます。mcp__puppeteer__* は puppeteer サーバーのすべてのツールに一致します。"*" や "mcp__*" のように先頭が固定されていない allow は、スキップされて何も自動承認しません。MCP ツールのパラメータで絞りたい場合は、--disallowedTools で deny ルールを渡します。

allow と deny の優先順位

公式ドキュメントによると、権限ルールは他の設定と同じ優先順位に従い、managed settings が最上位です。コマンドライン引数を含め、他のどの階層も managed の権限ルールを上書きできません。

どこか1つの階層で deny されたツールは、他の階層では allow できません。たとえば managed の deny は --allowedTools で上書きできず、--disallowedTools なら managed の定義を超えて制限を追加できます。ユーザー設定で allow、プロジェクト設定で deny の場合も deny が効き、逆にユーザーの deny はプロジェクトの allow を止めます。どのスコープの deny も allow より先に評価されるためです。禁止事項を確実に効かせたい場合は、deny で書くのが前提になります。managed settings の配布方法は公式ドキュメントで確認してください。

プロジェクトの allow は信頼ダイアログの後に有効になる

.claude/settings.json の permissions.allow と permissions.additionalDirectories は権限を広げる設定です。公式ドキュメントによると、そのフォルダのワークスペース信頼ダイアログを承認してから適用されます。ダイアログには、そのフォルダが与えるルールとディレクトリが一覧表示されます。deny と ask は制限するだけなので影響を受けません。

  • リポジトリ内:git リポジトリのルート単位で信頼が記録されます。サブモジュールのような入れ子のリポジトリは対象外です
  • リポジトリ外:起動したディレクトリ単位です
  • ホームディレクトリで起動:そのセッションの間だけ信頼を保持し、ディスクには書きません

ダイアログは対話セッションにしか出ません。claude -p や SDK では表示されず、プロジェクトの allow ルールは使われず、stderr に警告が出ます。信頼していないリポジトリで claude -p を実行する前には、--setting-sources user や --bare で読み込む内容を絞る方法があります。全プロジェクトに効かせたいルールは、ユーザー設定の ~/.claude/settings.json に書きます。

よくある質問

Bash(git *) と Bash(git log *) はどう違いますか?

Bash(git log *) は git log だけを許可し、Bash(git *) は git のすべてのコマンドを許可します。サブコマンドの前に * を置いた allow ルールは、起動時に警告されます。

出典: Configure permissions

ユーザー設定で allow、プロジェクト設定で deny にした場合はどうなりますか?

deny が効きます。公式ドキュメントによると、どのスコープの deny も allow より先に評価され、ある階層で deny されたものは他の階層で allow できません。

出典: Configure permissions

Bash(command:rm *) で rm を拒否できますか?

できません。複合コマンドで回避され得るため、Claude Code はこのルールを無視して起動時に警告します。Bash(rm *) の形で書いてください。
