What you can do with permission settings in settings.json

Claude Code (Anthropic's AI coding agent that runs in the terminal) follows the permission rules you write in .claude/settings.json in your working folder to block file reads and command execution, or to ask for confirmation before running them. There are three kinds of rules: deny prohibits, ask confirms every time, and allow permits without confirmation. The official docs explain that rules are evaluated in the order deny → ask → allow, and anything denied at any level cannot be used even if allowed elsewhere (as of writing).

Writing "don't read .env" in CLAUDE.md (the instruction file Claude Code reads at startup) is a request to the AI, whereas rules in settings.json are enforced by Claude Code itself. For company-wide rollout, distributing rules as a file rather than as prose avoids copy mistakes.

How to use

  1. Select the checks above and click "Save settings.json."
  2. Create a .claude folder inside your work folder and put the saved files there.
  3. Start claude in that folder and accept the trust prompt. You can confirm the rules were loaded with /permissions.

Some things are not stopped (known limitations)

In my testing, a Read(./.env) rule stopped Claude's read tool and cat .env. However, opening .env from inside a Python script still got through. The official docs also say these rules don't cover indirect reads and writes, such as a script opening the file itself. Likewise, Bash(curl *) is documented as not blocking calls made by path or wrapped in sh -c.

Use deny rules as a safety net against accidentally reading or sending files, and combine them with a practice of never keeping real API keys in the working folder. To enforce this across an organization, the official docs describe managed settings, which users can't override, and sandboxing.

FAQ

Where should I put settings.json?

This is .claude/settings.json in your work folder (the folder where you launch Claude Code). If you share it through Git, you can distribute the same rules to everyone who uses that folder. Personal-only settings go in .claude/settings.local.json, and personal settings shared across all projects go in ~/.claude/settings.json.

I added it to deny, but it could still be read

Deny doesn't work for methods Claude Code can't recognize as file reads, such as a script that opens a file internally. See "Known limitations" above. First, check with /permissions that your rules are loaded.

A confirmation prompt appears for commands you put in allow

A project's allow rules aren't used until you accept the trust prompt for that folder. Start claude once in interactive mode and accept it. deny and ask take effect regardless of that approval.

Is the content I enter sent anywhere?

No, it is not sent. This page runs on HTML and JavaScript only, and generation happens inside your browser. To count page views, only the URL of the page you opened is sent to the operator's server (no cookies or external analytics services are used. Details).

Should I avoid rules marked "not verified individually"?

The syntax follows the rules I confirmed in the official docs and on a real machine, but I haven't tested whether the rules themselves actually block anything. Before you distribute them, I recommend confirming locally, with dummy files or commands, that they block what you expect.
