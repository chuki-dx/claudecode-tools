CLAUDE.md vs. settings.json: what goes where

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • CLAUDE.md is a Markdown file where you write instructions for Claude. Claude loads it as context, but it is not an enforced setting.
  • settings.json is a JSON configuration file. According to the official docs, the client enforces settings rules regardless of what Claude decides.
  • Putting guidance such as coding conventions and work procedures in CLAUDE.md, and putting enforcement that blocks commands or files in settings, matches how the official docs organize things.

The difference in one line: context or enforcement

Claude Code (Anthropic's AI coding agent that runs in the terminal) has CLAUDE.md for writing instructions and settings.json for writing settings. Both affect its behavior, so before rolling them out company-wide, I sort out what belongs in which file.

According to the official docs, CLAUDE.md is a Markdown file that gives Claude persistent instructions. You write it in plain text, and Claude reads it at the start of a session. Claude treats it as context, not as an enforced setting. The more specific and concise the instructions are, the more consistently Claude is said to follow them.

The docs also say that if you want to block specific operations regardless of Claude's judgment, you should use a PreToolUse hook rather than CLAUDE.md. The split is: put requests you want followed in CLAUDE.md, and use an enforcement mechanism for operations you want stopped.

Where to put CLAUDE.md and what to write in it

The official docs describe CLAUDE.md as "a place to write down what you would otherwise have to explain every time." Put in facts you want available in every session, such as build commands, conventions, project structure, and "always do X" rules. For multi-step tasks or content relevant to only part of the codebase, the docs advise moving it to skills or path-scoped rules.

Four places to put it

  • Organization managed policy: Instructions for the whole organization, placed in a fixed location for each OS. Corporate IT or DevOps manages it, and it is shared with all users in the organization. Check the official docs for the location.
  • User instructions: ~/.claude/CLAUDE.md. Put your own preferences here that apply across all projects.
  • Project instructions: ./CLAUDE.md or ./.claude/CLAUDE.md. Because these are shared with the team through source control, write project standards rather than personal preferences.
  • Local instructions: ./CLAUDE.local.md. Personal preferences for this project only; add it to .gitignore.

The order above is the load order, from the broadest scope to the narrowest. Project instructions enter the context after user instructions. Files in directories above the working directory are loaded at startup, and files in subdirectories are loaded when they are needed.

Writing notes

The official docs recommend writing instructions specific enough to verify. For example, "Use 2-space indentation" instead of "Format code properly," and "Run npm test before committing" instead of "Test your changes." As a guideline, keep each file under 200 lines; longer files use more context and are followed less reliably. If instructions contradict each other, Claude may pick one arbitrarily, so review for outdated instructions and conflicts regularly.

Where settings.json lives and which location takes precedence

According to the official docs, settings are JSON keys that change how Claude Code behaves. They cover the model used at startup, which actions can run without confirmation, which files cannot be read, and what the organization enforces. Which file you write to determines the scope in which a setting takes effect.

  • User (~/.claude/settings.json): Applies to all of your projects. Use it for personal preferences such as theme, default model, and your own permission rules.
  • Shared project (.claude/settings.json): applies to everyone who works in that folder. If it's a git repository, commit it and distribute it that way. Use it for team permissions, hooks, plugins, and environment variables the project needs.
  • Project local (.claude/settings.local.json): applies only to you, and only in this project. If you create the file by hand, add it to .gitignore yourself.
  • Managed settings: distributed by the organization. Use them for security policies and regulatory compliance requirements.

When the same key appears in multiple files, the value from the higher-precedence level is used. The order of precedence is managed settings, command line, project local, shared project, and user. Lists such as permissions.allow are merged rather than overwritten. Some model-related keys follow different rules, so check the official docs.

The settings file is strict JSON, so // comments and trailing commas cause syntax errors. After saving, run /status to check which files were loaded. Edits to permissions and hooks take effect in a running session without a restart.

In the official docs' configuration example, allow under permissions contains Bash(npm run lint) and Bash(npm run test *), and deny contains Read(./.env) and Read(./.env.*). Keeping Claude from reading .env is done with deny rules, not with prose in CLAUDE.md.

What to put where: a rough guide

The official docs include a table on when to use managed settings versus managed CLAUDE.md. The idea is: technical enforcement goes in settings, and behavioral guidance goes in CLAUDE.md.

  • Blocking specific tools, commands, and file paths: permissions.deny (managed settings)
  • Enforcing sandbox isolation: sandbox.enabled (managed settings)
  • Environment variables and API provider routing: env (managed settings)
  • Login method and organization restriction: forceLoginMethod, forceLoginOrgUUID (managed settings)
  • Code style and quality guidelines, data handling and compliance notices, and behavioral instructions for Claude: managed CLAUDE.md

Settings also has keys that adjust how CLAUDE.md files are loaded. claudeMdExcludes excludes specific files, for example when a large monorepo pulls in other teams' CLAUDE.md files. To apply it only on your own machine, put it in .claude/settings.local.json.

{
  "claudeMdExcludes": [
    "**/monorepo/CLAUDE.md",
    "/home/user/monorepo/other-team/.claude/rules/**"
  ]
}

You can't exclude the managed policy CLAUDE.md. This ensures organization-wide instructions apply regardless of individual settings.

Notes for company-wide rollout

To share settings with your team, commit .claude/settings.json. If individuals want to override them for themselves, they can write to .claude/settings.local.json, which doesn't need to be committed.

Some committed settings do not take effect until each member trusts the folder. According to the official docs, this applies to permissions.allow rules, permissions.additionalDirectories, extraKnownMarketplaces, and most env values, while deny and ask rules apply immediately. Some keys also do not take effect when they come from files in the repository.

If your organization distributes managed settings, your own files and --settings cannot override the managed keys. Run /status to see which managed sources are in effect.

FAQ

If I write prohibitions in CLAUDE.md, will Claude reliably follow them?

It isn't reliable. According to the official docs, Claude treats CLAUDE.md as context, not as an enforced setting. If you want to block an operation regardless of Claude's judgment, the docs point you to a PreToolUse hook, and rules in settings are enforced by the client.

Source: How Claude remembers your project

What should I do if I don't want to commit my personal settings to the repository?

Use CLAUDE.local.md for CLAUDE.md, and .claude/settings.local.json for settings. Both are personal to you and apply only to this project. If you create them by hand, add them to .gitignore yourself.

Source: Settings files and precedence

If I set the same key in multiple settings.json files, which one is used?

The value from the higher level is used. The order of precedence is managed settings, command line, project local, shared project, then user. Lists such as permissions.allow are merged rather than overridden.
