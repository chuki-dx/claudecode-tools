Using Claude Code behind a proxy or with an internal corporate certificate (environment variables and how to verify)

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • According to the official docs, Claude Code (Anthropic's AI coding agent that runs in the terminal) configures proxies, custom certificate authorities (CAs), and mTLS through environment variables. Set them before launch; you can also specify them in settings.json.
  • By default, certificates trust both the bundled Mozilla CA store and the OS certificate store. A TLS-inspecting proxy is said to work with no extra configuration if its root certificate is in the OS and the runtime environment can read it.
  • SOCKS proxies are not supported. Configuration mistakes often show up later as connection errors, so check what was loaded with claude --debug and /status.

What you can do: configure three settings with environment variables

This article summarizes "Enterprise network configuration" in the official docs and is based on what it said as of writing (October 2026). These are not results I tested myself.

The official docs explain that you configure traffic through a corporate proxy, trust for a custom CA (a certificate authority that issues certificates inside your company), and mTLS (mutual TLS authentication with client certificates) using environment variables.

Set environment variables before you launch. A value you export in the shell is read only once at startup, so a running session won't pick up later changes.

Source: Enterprise network configuration

Proxy settings

Standard proxy environment variables are supported. An HTTPS proxy is recommended; specify an HTTP proxy only when HTTPS isn't available.

# HTTPS proxy (recommended)
export HTTPS_PROXY=https://proxy.example.com:8080

# HTTP proxy (if HTTPS not available)
export HTTP_PROXY=http://proxy.example.com:8080

Use NO_PROXY to specify destinations that should bypass the proxy. You can separate entries with spaces or commas.

# Bypass proxy for specific requests - comma-separated format
export NO_PROXY="localhost,192.168.1.1,example.com,.example.com"

Lowercase variables also work. The first one that is set is used, in the order https_proxy, HTTPS_PROXY, http_proxy, HTTP_PROXY.

Proxies that require authentication

If Basic authentication is required, include the credentials in the proxy URL.

export HTTPS_PROXY=http://username:password@proxy.example.com:8080

The official docs advise against writing passwords directly in scripts and recommend using environment variables or secure credential storage instead. For proxies that require advanced authentication such as NTLM or Kerberos, the docs suggest considering an LLM Gateway service that supports that authentication method.

Certificate settings: OS store, custom CA, mTLS

According to the official docs, by default Claude Code trusts both the bundled Mozilla CA certificates and the OS certificate store. Reading the OS store requires a runtime that has tls.getCACertificates. The native installer build always supports it; for npm installs, Node 22.15 or later is required. On older Node versions, only the bundled set and NODE_EXTRA_CA_CERTS are used.

A TLS-inspecting proxy works without extra configuration if its root certificate is in the OS trust store and the runtime can read it. If the proxy can't handle gzip-compressed request bodies correctly, you can turn compression off with CLAUDE_CODE_GZIP_REQUEST_BODIES=0.

Specify a custom CA directly

export NODE_EXTRA_CA_CERTS=/path/to/ca-cert.pem

You can also narrow trust sources with CLAUDE_CODE_CERT_STORE. Specify bundled (the bundled Mozilla CAs) and system (the OS) as a comma-separated list; the default is bundled,system. This variable has no dedicated settings.json key, so set it in the env block of ~/.claude/settings.json or in the process environment.

mTLS (client certificate)

# Client certificate for authentication
export CLAUDE_CODE_CLIENT_CERT=/path/to/client-cert.pem

# Client private key
export CLAUDE_CODE_CLIENT_KEY=/path/to/client-key.pem

# Optional: Passphrase for encrypted private key
export CLAUDE_CODE_CLIENT_KEY_PASSPHRASE="your-passphrase"

To renew a certificate, replace the files at the same paths. If a request fails with a connection reset or a TLS handshake error, Claude Code reloads both files and retries, so running sessions pick up the change without a restart. Before v2.1.232, connection errors did not trigger a reload. If the gateway responds with an HTTP error, the files are not reloaded; the change takes effect when the settings are applied or after a restart. Replace the files before they expire.

Checking whether settings were loaded

According to the official docs, Claude Code doesn't validate most settings when it loads them, so a wrong proxy address or certificate path shows up later as a connection error or certificate error on subsequent requests. The only thing checked at startup is the proxy URL; a value that can't be parsed, such as one missing http://, stops startup with an error that names the variable to fix.

To check before a request is sent, start Claude Code with debug logging.

claude --debug

The output goes not to the terminal but to ~/.claude/debug/<session-id>.txt, which you can change with --debug-file <path>. If the log has lines like the following, each file was loaded. If a file can't be loaded, a Failed to read or Failed to load line with a reason appears.

CA certs: Appended extra certificates from NODE_EXTRA_CA_CERTS (/etc/ssl/certs/corp-ca.pem)
mTLS: Loaded client certificate from CLAUDE_CODE_CLIENT_CERT
mTLS: Loaded client key from CLAUDE_CODE_CLIENT_KEY

You can also check from /status in an interactive session. The mTLS line appears only when the files were loaded successfully. The Additional CA cert(s) line only shows the path and doesn't confirm loading, so verify that one in the debug log.

Before you distribute: background agents and allowlists

Background agents started with claude agents, --bg, or /background are run by a per-user supervisor process. This process inherits the environment of the shell that first started it. If you only export proxy or CA variables in your shell, whether they take effect depends on which shell happened to start it. The official docs recommend putting them in the env block of ~/.claude/settings.json or managed settings. They state that only settings files reach all background sessions.

Add the hosts listed in the official docs to your proxy or firewall allowlist. For example, api.anthropic.com is for Claude API requests, claude.ai is for claude.ai account authentication, and platform.claude.com is for Console account authentication. With providers such as Amazon Bedrock, the destinations for model traffic and authentication are on the provider side. However, WebFetch calls api.anthropic.com unless you set skipWebFetchPreflight: true. For the full list of hosts, check the official docs.

FAQ

Can I use it through a SOCKS proxy?

According to the official docs, Claude Code does not support SOCKS proxies. Use an HTTPS proxy (recommended) or an HTTP proxy.

Source: Enterprise network configuration

How do I make Claude Code trust the certificate of our internal TLS inspection proxy?

According to the official docs, no extra configuration is needed if the proxy's root certificate is in the OS trust store and the runtime can read it. For npm installs, Node 22.15 or later is required. To specify it directly, set NODE_EXTRA_CA_CERTS to the path of the certificate file.

Source: Enterprise network configuration

How do I check whether the proxy and certificate settings are taking effect?

Start with claude --debug and check that the log shows a loading line, or run /status in an interactive session. /status can't confirm that a CA path was actually loaded, so verify it in the debug log.
