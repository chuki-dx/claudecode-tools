How to keep Claude Code activity logs for audits: OpenTelemetry and SIEM integration

Published: October 17, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • According to the official docs, the audit data source for Claude Code (an AI coding agent from Anthropic that runs in the terminal) is OpenTelemetry events, which carry user identifying attributes and can be sent to a SIEM through the OTLP log exporter.
  • Command and MCP details are recorded when you set OTEL_LOG_TOOL_DETAILS=1. (For the built-in server in sessions owned by Claude Desktop, mcp_server_name/mcp_tool_name are recorded even without the flag.) Because this can include sensitive content, enable it only when the collection destination is approved.
  • With authentication such as API keys or Bedrock, you have to attach user identity information yourself, and anomaly detection and alerting are the SIEM's job.

Audit data comes from OpenTelemetry events

According to the official docs, the audit data source for Claude Code activity is OpenTelemetry events (OpenTelemetry is a way to output monitoring data in a common format). Each event carries identifying attributes, so tool calls, MCP activity, and permission decisions can be tied to the user who performed them.

With the OTLP log exporter, you can send logs to a SIEM (a platform that collects and analyzes security-related logs) that has an OTLP receiver. You can also forward them to a SIEM through an OpenTelemetry Collector.

Pay attention to the division of responsibilities as well. Claude Code emits only a raw event stream; anomaly detection, baselining, correlation across sessions, and alerting are the responsibility of your SIEM or monitoring platform.

Source: Monitoring

Whose action it is recorded as

Standard attributes contain the authenticated user's identity. If you're signed in with a Claude account, they include user.email, user.account_uuid, user.account_id, and organization.id, plus user.id and a per-session session.id. user.id is a per-installation identifier (for sessions signed in to the Claude apps gateway with /login, it is the IdP subject).

In sessions started by a developer, MCP tool calls, Bash commands, and file edits are recorded as that developer's actions and do not run under a separate service account. Sessions in a Claude Tag channel run under the organization's shared identity.

For API keys, Bedrock, and similar setups

If you authenticate with a direct API key, Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry, only user.id and session.id are included. In that case, add user identification yourself with OTEL_RESOURCE_ATTRIBUTES, either in per-user settings within managed settings (settings that admins distribute) or in a launch wrapper. The values are the official examples.

export OTEL_RESOURCE_ATTRIBUTES="enduser.id=jdoe@example.com,enduser.directory_id=S-1-5-21-..."

Source: Monitoring

What each event tells you

The official docs include a table mapping the events you may want to monitor to the corresponding hook events. The main ones are as follows.

  • Whether a tool call was allowed or denied, and where the decision came from: tool_decision
  • Permission mode escalation: permission_mode_changed
  • Blocking with a policy hook: hook_execution_complete
  • Login, logout, authentication failures: auth
  • MCP server connections and failures: mcp_server_connection
  • Commands that ran and files touched: tool_result (executed), tool_decision (denied). This requires OTEL_LOG_TOOL_DETAILS=1.

Keep detailed logs of MCP operations

To keep detailed records of MCP operations, enable a log exporter and set OTEL_LOG_TOOL_DETAILS=1. The server name, tool name, and call arguments are recorded along with identifying attributes.

If you don't set it, the tool_name of a user-configured MCP server is replaced with the fixed string "mcp_tool", and the arguments are not shown. mcp_server_connection does not include server_name or the error message. Claude Desktop's built-in servers have exceptions and version requirements, so check the official docs.

Source: Monitoring

Configuring SIEM delivery and verifying connectivity

Point OTEL_EXPORTER_OTLP_LOGS_ENDPOINT at your SIEM's OTLP receiver, or at an OpenTelemetry Collector that forwards to your SIEM's ingestion API. The managed settings example in the official docs outputs events only and enables tool details for MCP and Bash auditing.

{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_LOG_TOOL_DETAILS": "1",
    "OTEL_EXPORTER_OTLP_LOGS_PROTOCOL": "http/protobuf",
    "OTEL_EXPORTER_OTLP_LOGS_ENDPOINT": "https://siem.example.com:4318/v1/logs",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer your-siem-token"
  }
}

To check connectivity, send a prompt in a session with this configuration and see whether a claude_code.user_prompt event arrives in your SIEM. If it doesn't, start with claude --debug-file <path> and look for [3P telemetry] export errors in the log. The endpoint and token are example values.

Source: Monitoring

What gets recorded and what to watch for

OpenTelemetry output is opt-in and requires explicit configuration, and events do not include raw file contents or code snippets. However, enabling items that are not recorded by default may bring sensitive content in.

  • Prompts: by default, only the length is recorded. You can include the content with OTEL_LOG_USER_PROMPTS=1, and in the user_prompt event it appears in both prompt and prompt_text. To exclude it in your collector, specify both.
  • Response text: By default, only the length is included. To include the text, set OTEL_LOG_ASSISTANT_RESPONSES=1. If it is unset, the value of OTEL_LOG_USER_PROMPTS is used instead, so if you want to include only prompts, set OTEL_LOG_ASSISTANT_RESPONSES=0.
  • Tool arguments: Not recorded by default. With OTEL_LOG_TOOL_DETAILS=1, they include Bash commands, MCP server and tool names, file paths, and so on.
  • user.email: Included when you authenticate with OAuth, and it is sent only to the OTel endpoint you configured (it is not sent to Anthropic). If this is a concern, exclude or mask it in your backend.

The official docs say that the details from OTEL_LOG_TOOL_DETAILS=1 can contain the same sensitive content as the session itself, so enable it only if the collection destination is approved. Traces and raw API bodies (OTEL_LOG_RAW_API_BODIES) can include the entire conversation history through a separate path, so check the official docs before using them. This is based on the official docs as of writing (October 2026).

You can standardize local retention with cleanupPeriodDays in managed settings, and use the retention_sweep event to confirm that each machine is actually applying it.

FAQ

If I use an API key or Bedrock, will the audit log record who performed an action?

According to the official docs, in this case there is no Claude account, so only user.id and session.id are included. To identify users, add your own identifying information with OTEL_RESOURCE_ATTRIBUTES.

Source: Monitoring

Are prompt contents also recorded in the audit log?

By default, the content is not collected and only the length is recorded. Setting OTEL_LOG_USER_PROMPTS=1 includes the content, but it may contain sensitive information, so check how the destination handles it.

Source: Monitoring

What should I check when events don't reach my SIEM?

The official docs say to first send a prompt and check for the claude_code.user_prompt event. If it doesn't arrive, start with claude --debug-file <path> and look for [3P telemetry] export errors in the log.

Source: Monitoring
