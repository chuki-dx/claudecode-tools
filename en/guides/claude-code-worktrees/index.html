How to run Claude Code in parallel with worktrees, and caveats

Published: October 17, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • Start with a name for --worktree (or -w) and you get an isolated session with its own branch and directory. Run it again with a different name in another terminal and you have parallel work.
  • A worktree is a fresh checkout, so you need to initialize the environment, for example by installing dependencies. Gitignored files such as .env can be carried over with a .worktreeinclude file.
  • There are conditions around cleanup on exit, behavior with -p, and isolation limits such as being unable to block cp. Check them before you roll this out company-wide.

What worktrees do: split sessions and work in parallel

In Claude Code (Anthropic's AI coding agent that runs in the terminal), you can run multiple sessions in parallel using worktrees (separate working directories created from the same repository). This article is based on the official docs as of writing (October 2026).

According to the official docs, passing a name to --worktree or -w creates an isolated worktree and starts Claude inside it. By default, it is created under .claude/worktrees/<name>/ at the repository root, on a new branch named worktree-<name>.

claude --worktree feature-auth

If you run the same command in another terminal with a different name, a second isolated session starts. If you omit the name, Claude generates one such as bright-running-fox.

Source: Run parallel sessions with worktrees

Settings and Precautions Before Launch

According to the official docs, interactive runs require workspace trust. In a directory you are using for the first time, run claude once first and accept the trust dialog. If you haven't accepted it, --worktree exits with an error. Non-interactive runs with -p skip the trust check, so claude -p --worktree proceeds as is.

If you add .claude/worktrees/ to .gitignore, the contents of worktrees won't show up as untracked files in the main checkout.

Initializing the environment

A worktree is a fresh checkout. Ask Claude to install dependencies, or run your project setup in the worktree directory under .claude/worktrees/. To automatically bring gitignored files such as .env into a new worktree, add a .worktreeinclude file. Check the official docs for the syntax.

When asking during a session

If you ask "work in a worktree" during a session, it is created with the EnterWorktree tool. When entering a path outside the repository's .claude/worktrees/, the working directory, write permissions, and settings such as CLAUDE.md change, so you are asked for approval. This prompt can't be suppressed by a permission rule or "don't ask again"; only bypassPermissions mode skips it. Before v2.1.206, you could enter without confirmation.

Cleanup at the end and cautions about deletion

When you end an interactive session, Claude checks whether anything would be lost on deletion: changes, untracked files, uncommitted work in submodules, and new commits. This applies to worktrees created with git.

  • If clean: an unnamed session automatically deletes the worktree and branch. A named session asks for confirmation first.
  • If work remains: you are asked whether to keep or remove it. If you keep it, the directory and branch stay, and you can return with the claude --worktree <name> --resume command shown on exit. If you remove it, the work is deleted with it.
  • If Claude Code can't verify the state: it doesn't delete anything automatically. It shows what it couldn't verify and asks you.

Non-interactive runs with -p have no prompt on exit, so the worktree is not cleaned up. The lock created at creation also stays until a later session releases it. Delete it with git worktree remove, and if the lock causes a refusal, run git worktree unlock first.

On Windows, for links inside a worktree (NTFS junctions and directory symlinks), only the link is deleted and the target remains. Before v2.1.205, a link in a subdirectory could cause its target to be deleted.

Source: Run parallel sessions with worktrees

Isolation checks and limits

In an isolated worktree session, tool calls are blocked by the following four checks. This applies whether you started with --worktree, used EnterWorktree, or resumed a session, and it also applies to subagents that Claude launches.

  • File edits: when Edit, Write, or NotebookEdit target paths in the main checkout.
  • Command working directory: when the working directory of Bash, PowerShell, or Monitor commands becomes the main checkout, or when it cannot be confirmed that it stays outside.
  • Git redirection: git -C, --git-dir, the GIT_DIR and GIT_WORK_TREE variables, and Bash or Monitor commands that use cd to point git at the main checkout.
  • Command shape: Bash or Monitor commands where the text alone doesn't let you confirm that git stays inside the worktree. You cannot turn this check off.

However, these do not track files written by shell commands. A cp or shell redirect that writes to the main checkout without running git is not rejected, and is handled like any ordinary shell command by the permissions and sandboxing settings. For PowerShell, only the working directory check applies.

Source: Run parallel sessions with worktrees

What is shared with the main checkout

A worktree has its own files and branch, but it shares the following. This is the same whether you use --worktree or git worktree add.

  • The .git directory: it writes to the shared .git and also allows sandboxing, so git commit works even with the sandbox enabled.
  • Plugins: a plugin installed at project scope in the main checkout is also loaded in worktrees of the same repository. This requires v2.1.200 or later.
  • Approving permissions: If you choose "Yes, and don't ask again" for a Bash command in a worktree, it is saved to .claude/settings.local.json in the main checkout and applies to your other worktrees too. Where the repository root isn't used, such as on Windows, it stays within that worktree. Before v2.1.211, it was saved inside the worktree and lost when the worktree was deleted.
  • Untracked skills, agents, and commands: If the worktree root has no .claude/skills, the main project's skills are loaded. For skills, v2.1.277 or later is required.

When to use a hook

${CLAUDE_PROJECT_DIR} stays at the project root where the session started, even after you enter a worktree. A hook that needs the worktree path should read cwd from the input JSON. In a worktree session started from the desktop app, settings, hooks, and similar are read from the root of the main checkout, while CLAUDE.md and .claude/rules/ are read from the worktree.

Source: Run parallel sessions with worktrees

FAQ

Can a worktree session ever modify files in the main checkout?

According to the official docs, Edit, Write, and NotebookEdit operations that target paths in the main checkout are blocked. However, cp and shell redirects that write without running git are not denied by this check. They are handled by the permissions and sandboxing settings, so you need to review those settings.

Source: Run parallel sessions with worktrees

Is a worktree started with -p deleted automatically on exit?

No. According to the official docs, non-interactive runs with -p have no confirmation at exit, and the worktree is not cleaned up. To delete it, run git worktree remove; if the removal is refused because of a lock, run git worktree unlock first.

Source: Run parallel sessions with worktrees

Can I bring gitignored files such as .env into a new worktree?

According to the official docs, adding a .worktreeinclude file lets you automatically bring files into new worktrees. The source doesn't describe the syntax in detail, so check the official docs.

Source: Run parallel sessions with worktrees
