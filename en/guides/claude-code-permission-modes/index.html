Claude Code Permission Modes Compared: Choosing Between default, acceptEdits, plan, and auto

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • A permission mode is a setting that determines what Claude can do without asking for confirmation. The official docs list default, acceptEdits, plan, auto, dontAsk, and bypassPermissions.
  • Choose by purpose: acceptEdits if you'll review changes afterward, plan if you want to inspect before changes are made. bypassPermissions is only for isolated containers or VMs.
  • auto can reduce confirmation prompts, but it doesn't guarantee safety, and it has conditions tied to the model and organization settings. This is based on the official docs as of writing (October 2026), so check the latest documentation before adopting it.

What changes with permission modes: the differences among the six modes

Claude Code (an AI coding agent from Anthropic that runs in the terminal) has permission modes. According to the official docs, a permission mode sets which actions can run during a session without confirmation. It changes whether Claude stops to ask before editing files, running shell commands, or accessing the network.

  • default: Only reads can run without confirmation. Suited to work where you want to review everything yourself, and to sensitive work.
  • acceptEdits: reads, file edits, and common file operation commands such as mkdir, touch, mv, and cp. It suits reviewing and fixing code as you go.
  • plan: Mostly read-only. It's meant for cases where you want to explore the codebase before making changes.
  • auto: Runs everything, with safety checks running in the background. It suits long tasks and situations where you want fewer repeated confirmations.
  • dontAsk: runs only reads within the working directory and pre-approved tools, and denies any action that would require confirmation. Intended for CI and scripts.
  • bypassPermissions: runs everything. Use it only in isolated containers or VMs.

default is displayed as Manual in the CLI, VS Code, the desktop app, and other places. The setting value is default, and in the CLI you can also use the alias manual.

The mode is the baseline, and you can layer permission rules on top to pre-approve or block specific tools. Deny rules take effect in every mode, including bypassPermissions, but allow rules have no effect in bypassPermissions.

Starting mode and how to switch

The official docs explain that when you start a new session in the terminal, the first item below that applies is used.

  1. The --permission-mode flag, or --dangerously-skip-permissions
  2. permissions.defaultMode in a settings file
  3. Built-in defaults

The built-in default is auto in the interactive terminal and VS Code on Claude Code v2.1.283 or later. In earlier versions it applied to the Pro, Max, and Team plans, and it also varies with claude -p and organization settings. If you specify nothing, sessions may start in auto, which asks for fewer confirmations, so it is safer to set the startup mode explicitly before you distribute.

This is an example of specifying it just once.

claude --permission-mode plan

To make default the default for all sessions, write the following in ~/.claude/settings.json.

{
  "permissions": {
    "defaultMode": "default"
  }
}

In a terminal, permissions.defaultMode in the project's .claude/settings.json accepts any value other than auto and bypassPermissions. The VS Code extension doesn't read project settings for the starting mode.

Switching during a session

In the CLI, switch modes with Shift+Tab. From auto, the first press goes to default, and after that the order is default, acceptEdits, plan. dontAsk is not part of the cycle; specify it with --permission-mode dontAsk. In VS Code, choose the mode from the mode indicator below the prompt box.

When to use acceptEdits and plan

acceptEdits creates and edits files in the working directory without asking for confirmation. mkdir, touch, rm, rmdir, mv, cp, and sed are also auto-approved, but only for paths inside the working directory or additionalDirectories. Writes to protected paths and any Bash commands other than the built-in read-only ones still prompt for confirmation. It suits a workflow where you review changes afterward with something like git diff.

plan only investigates and writes a plan, and doesn't edit source. Edits are blocked until you approve the plan. However, in an interactive terminal where bypass permissions is available, this block isn't enforced. Enter it with Shift+Tab, or by putting /plan at the start of a single prompt.

When you approve a plan, you choose from Yes, and use auto mode, Yes, manually approve edits, and No, keep planning.

The convenience and caveats of auto mode

In auto mode, a separate model (a classifier) reviews each action before it runs and blocks actions that go beyond what you asked for, as well as actions that appear to have been steered by content Claude read. The official docs note that this reduces prompts but does not guarantee safety, and that it should not replace review of sensitive operations.

There are model requirements: older models such as Sonnet 4.5, Opus 4.5, and Haiku 4.5 are not supported on any provider. It is available by default on Team and Enterprise, but an admin can disable it by setting permissions.disableAutoMode to "disable" in managed settings. If it is unavailable, the session starts in Manual mode.

Examples blocked by default include downloading and running code, sending sensitive data externally, production deployments, and force pushes. File operations inside the working directory and read-only HTTP requests are allowed. After 3 blocks in a row, or 20 in total, auto mode pauses and returns to asking for confirmation.

Boundaries you state in conversation, such as "don't push," are referenced by the classifier, but they are not saved as rules and may be lost when the context is compacted. If you need to block something reliably, use a deny rule.

dontAsk, bypassPermissions, and what stays the same in every mode

dontAsk automatically denies every operation that would normally prompt for confirmation. It's meant for CI, where you decide the allowed scope in advance. The example from the official docs is below.

claude -p "run the test suite" --permission-mode dontAsk --allowedTools "Bash(npm test)" "Read"

bypassPermissions disables permission prompts and safety checks. The official docs warn to use it only in isolated environments, and note that it offers no protection against prompt injection or unintended actions. A session can't switch into it unless it was enabled at startup, and on Linux and macOS Claude Code refuses to start as root or with sudo (this check is skipped inside a recognized sandbox). Administrators can block it by setting permissions.disableBypassPermissionsMode to "disable".

Some things are never auto-approved in any mode. Examples are tools that match an ask rule, and rm or rmdir targeting important paths such as the root or home directory. Writes to protected paths such as .git and .claude are also not auto-approved, except in bypassPermissions mode and in plan mode sessions running in an interactive terminal where bypass permissions is available.

FAQ

Is Manual mode different from default?

They are the same mode. The UI calls it Manual, while settings values, hooks, and the SDK call it default. In the CLI, manual also works as an alias.

Source: Choose a permission mode

Which mode does it start in if I configure nothing?

According to the official docs, in the interactive terminal and VS Code on Claude Code v2.1.283 or later, the built-in default is auto. If auto is not available, it starts in Manual. Check the official docs for the detailed conditions.

Source: Choose a permission mode

Is it OK to let people use bypassPermissions internally?

The official docs describe this as a mode to use only in isolated environments such as containers or VMs. If you don't want people to use it, an admin can set permissions.disableBypassPermissionsMode to "disable" in managed settings.
