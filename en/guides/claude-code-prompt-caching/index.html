How Claude Code prompt caching works: what keeps it and what breaks it

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • Prompt caching in Claude Code (Anthropic's AI coding agent that runs in the terminal) works automatically and reuses the portion at the start of a request that matches exactly.
  • The cache is invalidated by switching models, /compact, changing tool definitions, and similar actions. It is not invalidated by editing CLAUDE.md, changing the permission mode, /rewind, and so on.
  • The basic approach is to avoid operations that can be cut off mid-task, and to check how close you are to the limit with /usage.

How it works: the matching beginning of the request is reused

The following is a summary based on the official docs as of writing (October 2026), not the result of my own testing. According to the official docs, the model remembers nothing between requests, so Claude Code resends the entire payload every time: the system prompt, project context, past messages and tool results, and the new message. New content is appended at the end, so most of it is identical to the previous request.

The API reuses the start of a request (the prefix) by matching it against content it processed recently. The match must be exact, and if anything changes partway through, everything after that point is recomputed. There is no per-file cache. Reused portions are billed at the cached-token rate.

In order from least likely to change, they form the following 3 layers.

  • System prompt: the base instructions and tool definitions. It changes when the set of tool definitions changes.
  • Project context: CLAUDE.md, auto memory, and so on. It changes at session start and after /clear and /compact.
  • Conversation: messages, responses, and tool results. It changes every turn.

If only the conversation layer changes, the other two layers stay in the cache, but if the system prompt changes, the whole cache is invalidated. In addition, the cache is separate for each model, and for many models it is also separate for each effort level.

Actions that break the cache: switching models, changing tool definitions, /compact, and more

When the cache expires, only the next turn is slower and costs more, and after that the new prefix is cached.

Model, effort, and fast mode

When you switch models with /model, the next request reads the entire history without the cache, even if the content is the same. In the terminal, a confirmation appears only when the cache is warm and the model you are switching to is not the one that generated the previous response. With opusplan, each plan mode switch counts as a model switch, and so does the turn of a skill or command that specifies a different model in its frontmatter.

Changing effort works the same way for many models. However, if you use Opus 5.5, Sonnet 5.5, Haiku 5.5, or Fable 5.1 with an API key or a Claude subscription, the cache is preserved. This does not apply to Amazon Bedrock, Google Cloud's Agent Platform, Claude apps gateway, when CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS is set, or to organizations with a HIPAA configuration.

When you turn on fast mode, the first request is made without cache. The cost is incurred once per conversation, so the earlier in a session you turn it on, the cheaper it is.

Tool definitions

Tool definitions sit in the system prompt layer, so the cache is invalidated when the set of tools changes. If MCP tool search is loading tools lazily (the default on supported models), connecting or disconnecting servers has no effect. If tools are loaded up front, for example because tool search is disabled, the cache is invalidated when definitions are added, or removed through deny rules or by disabling them in /mcp. If tool search is unavailable or disabled, adding a deny rule with only a tool name (such as Bash) removes the definition from the next request and invalidates the cache. Scoped deny rules such as Bash(rm *), and allow and ask rules, have no effect.

Compaction and other topics

/compact replaces the history with a summary, so the conversation layer of the cache is invalidated. However, the summarization request reads the prefix if the cache is still warm, so it costs less than the context size would suggest. Resuming an old session after the cache lifetime has expired is the most expensive case.

The conversation is also cut off when Claude Code deletes old images after they accumulate, and in the first conversation after a Claude Code upgrade. Auto-updates are applied at the next launch, not in the middle of a session.

What can't be cut off: CLAUDE.md edits, permission modes, /rewind, and more

The following actions are appended to the end of the conversation or don't touch the request, so the cache is preserved.

  • File edits: a <system-reminder> announcing the change is appended, and Claude re-reads the file if needed.
  • Editing CLAUDE.md: It is read once at session start, so editing it mid-session doesn't break the cache, but the changes aren't picked up either. New content is loaded on the next /clear, /compact, or restart.
  • Changing the permission mode: with opusplan, however, this counts as a model switch.
  • Output style changes: They apply from the next message. Before v2.1.251, they didn't take effect until /clear or a new session.
  • Skill and command invocations and /recap: they are appended to the history rather than replacing it.
  • /rewind: hits an earlier cache entry. The official docs say to use it instead of /compact for work you want to abandon.
  • Subagents: They don't affect the parent's cache, but their first request doesn't read the parent's cache and instead builds its own.

Cache lifetime (TTL) and settings

The cache expires after a period of inactivity, and each cache hit resets the timer. The first turn after a long break can be slower. There are two TTLs, 5 minutes and 1 hour. The 1-hour TTL holds up better across long breaks, but cache writes cost more.

According to the official docs, when you don't choose a TTL yourself, a 1-hour TTL is requested only on a Claude subscription while you're within the plan's included usage. With API keys, cloud providers, and usage credits, the main conversation also uses 5 minutes.

You can set the TTL for the main conversation with the promptCacheTtl setting or the CLAUDE_CODE_PROMPT_CACHE_TTL environment variable. The only valid values are 5m and 1h. Requires v2.1.242 or later.

The cache is effectively scoped to one machine and one directory, so sessions in different directories do not hit each other's caches.

Checking that it works, and cautions for company use

The API returns cache_creation_input_tokens (writes to the cache) and cache_read_input_tokens (reads from the cache) with each response. High reads mean caching is working well; if writes stay high on every turn, something in the prefix keeps changing.

For a single session, run /usage. After the first response in the main conversation, a Prompt cache (main) line is added, showing the hit rate, the number of misses, and whether the cache is currently warm. This display requires v2.1.251 or later. For the whole organization, the OpenTelemetry exporter reports token counts per user and session.

On Amazon Bedrock and similar platforms, the cache lives on the cloud provider's side. Through an LLM gateway or a custom ANTHROPIC_BASE_URL, whether caching works depends on the gateway. If a gateway strips the cache_control marker while still returning success, the entire conversation history is billed as uncached input on every turn.

To disable it, set DISABLE_PROMPT_CACHING to 1. The official docs say to do this only for debugging and to leave it enabled otherwise.

FAQ

Does editing CLAUDE.md during a session invalidate the cache?

It won't cut the session off, but your edits won't take effect. The project-root and user-level CLAUDE.md files are read at session start, and the new content is loaded on the next /clear, /compact, or restart.

Source: How Claude Code uses prompt caching

Why is the next response slower after I switch models?

Because each model has its own cache. Even if the content is the same, the next request reads the entire conversation history without the cache.

Source: How Claude Code uses prompt caching

Where can I check whether caching is working?

Run /usage to see the hit rate and miss count on the Prompt cache (main) line. This display requires v2.1.251 or later.
