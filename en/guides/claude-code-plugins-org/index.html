Managing Claude Code plugins in an organization: settings for distribution, required plugins, and install restrictions

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • According to the official docs, Claude Code (Anthropic's AI coding agent that runs in the terminal) plugins can be distributed to all machines and enabled by writing extraKnownMarketplaces and enabledPlugins together in managed settings.
  • You can restrict install sources with strictKnownMarketplaces (allowlist) and blockedMarketplaces (blocklist). To also block loading from local paths or URLs, use disableSideloadFlags together with them.
  • There is no key for showing different things to different users or groups, or for hiding /plugin. This is based on the official docs as of writing (October 2026), so check the latest documentation before you roll it out.

What you can do: the big picture of distributing, requiring, and restricting

According to the official docs, a marketplace is a catalog of plugins that Claude Code fetches from a git repository, a URL, or a local path. Once you register one on your machine, you can install plugins from it.

To roll out to many machines, set two keys at the same time in managed settings (a policy file read by every device in the organization, or a policy delivered from a server). extraKnownMarketplaces registers the marketplace on each machine, and enabledPlugins names the plugins to install and enable from it.

Source: Manage Claude Code plugins for your organization

How to deliver managed settings to devices

There are three ways to deliver managed settings.

  • Server-managed settings: In Organization settings > Claude Code > Managed settings, set the plugin keys as JSON. You need the Owner role in your Claude organization.
  • MDM policy: on macOS, distribute a plist with the settings keys at the top level. On Windows, store the entire JSON document as a string in a registry value.
  • Managed settings file: place managed-settings.json in the platform's system path. You can also add files to the managed-settings.d/ directory next to it.

The official docs say to use server-managed settings if you have a Claude for Teams or Enterprise organization on claude.ai and not all devices are under MDM; otherwise, use MDM or a file.

Notes when using multiple paths

By default, only one of the three sources applies on a given machine. Claude Code checks server-managed settings, then MDM, then files, and uses the first one that delivers a policy key. If server-managed settings deliver even one unrelated key, the plugin keys from MDM or files on that device are ignored (except keys that are read from all sources). To apply all sources, set managedSourcesBehavior to "merge".

Source: Manage Claude Code plugins for your organization

Settings to require plugins

Add a marketplace to extraKnownMarketplaces, using the name from its marketplace.json as the key. Add plugins to enabledPlugins in the form plugin-name@marketplace-name. The following example registers an organization marketplace and force-enables two plugins.

{
  "extraKnownMarketplaces": {
    "your-marketplace": {
      "source": { "source": "github", "repo": "your-org/your-marketplace" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": {
    "code-formatter@your-marketplace": true,
    "deploy-helper@your-marketplace": true
  }
}

Once the settings arrive, the marketplace is registered and the plugin is installed at the user's next session start, and it appears in /plugin. Managed settings take precedence over every other scope, so a user disabling the plugin in their own scope does not stop it from loading. To block it in all scopes and hide it from the list, set it to false in the managed enabledPlugins.

A caution: if the marketplace is a private git repository, each user needs read access, and the clone runs without confirmation using the credentials already stored in git on each person's machine. In -p and CI runs, plugin installation proceeds in the background, so a plugin may be missing on the first turn. Setting CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1 makes it wait for installation before the first query.

If you only need it for one repository, you can write the same key in that repository's .claude/settings.json. However, extraKnownMarketplaces applies only in trusted folders and is silently ignored in untrusted ones.

Restricting install sources

The allowlist and denylist are checked against the source of the marketplace that a plugin comes from, not against individual plugins inside the marketplace. They apply before download (adding, installing, updating, auto-updating, and so on), and they are also re-applied to installed plugins at session start. Plugins that don't match are not loaded.

  • An empty allowlist [] blocks all sources, including the official marketplace.
  • The deny list is checked before the allow list, and a source that appears in both is blocked.
  • For github and git entries in the allowlist, repo, url, ref, and path must match. A trailing slash or the presence of .git is treated as a different value. If a repository can be cloned from multiple URLs, hostPattern is recommended.
  • You can allow all repositories under an owner at once, as in { "source": "github", "repo": "your-org/*" } (Claude Code v2.1.223 or later).

If you set an allowlist without including { "source": "skills-dir" }, plugins placed in places like ~/.claude/skills/ as folders containing .claude-plugin/plugin.json will no longer be loaded.

A typical configuration that allows only the official marketplace and your own is shown below. It also registers both, force-enables two plugins, and denies --plugin-dir.

{
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "anthropics/claude-plugins-official" },
    { "source": "github", "repo": "your-org/*" },
    { "source": "skills-dir" }
  ],
  "extraKnownMarketplaces": {
    "claude-plugins-official": {
      "source": { "source": "github", "repo": "anthropics/claude-plugins-official" }
    },
    "your-marketplace": {
      "source": { "source": "github", "repo": "your-org/your-marketplace" }
    }
  },
  "enabledPlugins": {
    "code-formatter@your-marketplace": true,
    "deploy-helper@your-marketplace": true
  },
  "disableSideloadFlags": true
}

On machines with this setting, adding a source that is not on the allowlist fails with a message containing is blocked by enterprise policy. The allowlist doesn't register anything itself, so you also need to register sources explicitly with extraKnownMarketplaces.

What managed settings can't do, and how to verify

The official docs list common requests from security reviews that the current settings schema has no dedicated key for.

  • Per-user and per-group application: Every plugin key applies to all users who receive the settings. Server-managed settings are a single configuration for the whole organization. To target groups, use endpoint-managed settings or a gateway policy.
  • Blocking a specific plugin within an allowed marketplace: set it to false in the managed enabledPlugins.
  • Hiding /plugin: there is no key that disables it. The closest setup combines an allowlist of only your company's marketplace, enabledPlugins for the plugins you distribute, and disableSideloadFlags.
  • Control of --plugin-dir: Allowlists don't apply to it; disableSideloadFlags rejects it.
  • Plugin toggles in claude.ai: Organization settings > Plugins & skills does not set the keys described here. Settings made there reach the CLI as synced plugins, which have separate controls.

Checks after distribution

On a single machine, start Claude Code, run /plugin, and check that the marketplaces and plugins are listed. In CI, run claude -p with --output-format stream-json --verbose and check plugins in the init event.

FAQ

Can users disable plugins themselves?

A plugin enabled through enabledPlugins in managed settings is loaded even if the user disables it in their own scope, because managed settings take precedence over every other scope. To disable it in all scopes, set it to false on the managed side.

Source: Manage Claude Code plugins for your organization

Can I also block --plugin-dir by setting an allowlist?

You can't block it that way. According to the official docs, the allowlist does not apply to --plugin-dir; disableSideloadFlags rejects it instead. This key also rejects --plugin-url and similar flags at startup.

Source: Manage Claude Code plugins for your organization

Can I distribute a plugin to only specific departments?

There is no dedicated key. Plugin keys apply to all users who receive the settings, and server-managed settings are a single configuration per organization. The docs list endpoint-managed settings or gateway policies for per-group control, so check the official docs for details.
