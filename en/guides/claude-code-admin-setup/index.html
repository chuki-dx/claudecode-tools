Admin setup flow for rolling out Claude Code in an organization: distributing managed settings and what you can restrict

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • According to the official docs, organization policies for Claude Code (Anthropic's AI coding agent that runs in the terminal) are distributed through managed settings and take precedence over users' local settings.
  • The order of decisions is: API provider, how settings are delivered, the scope of restrictions, visibility into usage, and data handling.
  • After you configure it, ask users to run /status to confirm that the managed settings are in effect.

First, decide on an API provider

According to the official docs, managed settings can be distributed through the Claude admin console, MDM (a system for managing devices in bulk), or files on disk. SSO, SCIM, and seat assignment are configured on the Claude account side and are covered in a separate admin guide.

The provider affects billing, authentication, which compliance obligations carry over, and which features are available.

  • Claude for Teams / Enterprise: for when you want Claude Code and claude.ai under a single per-seat contract. It requires no infrastructure operations and is the default recommendation.
  • Claude Console: if you focus on the API or want pay-as-you-go billing.
  • Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry: for when you want to keep your existing cloud controls and billing.

One caveat: cloud sessions, Routines, Code Review, Remote Control, and the Chrome extension require a claude.ai account. A Console API key or cloud provider credentials alone won't work. If you plan to roll out through a cloud provider, first consider whether you also need Teams / Enterprise seats.

How Managed Settings Are Delivered and Their Precedence

According to the official docs, the following four are used in order of priority.

  • Server-managed settings (the claude.ai admin console): highest priority, and applies to all platforms.
  • plist / registry: com.anthropic.claudecode on macOS, HKLM\SOFTWARE\Policies\ClaudeCode on Windows.
  • Files: on macOS, /Library/Application Support/ClaudeCode/managed-settings.json; on Linux and WSL, /etc/claude-code/managed-settings.json; on Windows, C:\Program Files\ClaudeCode\managed-settings.json.
  • Windows user registry HKCU\SOFTWARE\Policies\ClaudeCode: lowest priority, Windows only.

Server-managed settings are fetched at startup and refreshed hourly during a session. Delivery through the admin console requires a Claude for Teams or Enterprise plan. If you use Bedrock or similar, you can run the Claude apps gateway to get the same remote delivery, and file-based or OS-level methods also work.

When providers are mixed, combine server-managed settings with file, plist, or registry alternatives. The docs note that plist and HKLM need administrator rights to write and are harder to tamper with, while HKCU can be written without elevation, so treat it as a convenience default rather than an enforcement mechanism.

With a few exceptions, managed values take precedence over user settings and project settings. Arrays such as permissions.allow and permissions.deny merge entries from all sources, so developers can add entries but cannot remove the ones set by the managed side.

What to restrict

Managed settings can control tools, commands, MCP servers, plugin sources, hooks, and more. The main items are as follows.

  • Permission rules: Use permissions.allow and permissions.deny to allow, ask about, or deny specific tools and commands.
  • Locking down permissions: allowManagedPermissionRulesOnly makes managed settings the only source of permission rules, and permissions.disableBypassPermissionsMode disables --dangerously-skip-permissions.
  • Sandbox: OS-level file and network isolation. It uses sandbox.enabled and sandbox.network.allowedDomains.
  • MCP servers: restrict which servers can be connected with allowedMcpServers, deniedMcpServers, and similar settings.
  • Models and versions: use availableModels to limit which models can be selected, and minimumVersion to keep auto-updates from dropping below a floor. requiredMinimumVersion refuses to start at all if the version is out of range.

One caveat: permission rules and the sandbox are separate layers. Even if you deny WebFetch, curl and wget can reach any URL as long as Bash is allowed, so the docs explain that you should add a sandbox with an OS-level domain allowlist.

If users sign in through claude.ai or the Anthropic API on a Claude Enterprise plan, you can set model restrictions, the default model, and the effort cap from the organization's admin console without distributing managed settings. However, these settings do not reach Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry, so for those use availableModels, model, and maxEffortLevel in managed settings.

Usage visibility and data handling

The official docs note that the available features differ between Teams / Enterprise and Console, and advise checking the availability column before planning your reporting.

  • Usage: OpenTelemetry can export sessions, tools, and tokens. This applies to all providers.
  • Analytics dashboards: Teams / Enterprise and the Console have separate screens. In Teams / Enterprise, you view per-user usage and spend in the spend report, not the dashboard.
  • Spend management: for Teams / Enterprise, it's an organization setting; for Console, it's the workspace limit. With third-party clouds, use the cloud provider's budget controls or the Claude apps gateway.

On data, Anthropic is said not to train models on your code or prompts under the Team, Enterprise, Claude API, and cloud provider plans. Retention periods and compliance are determined by the provider. Zero Data Retention (ZDR) is available to eligible Claude for Enterprise accounts. If you need per-request audit logs, setting up a gateway is recommended, but sessions through a gateway are outside the HIPAA configuration.

Post-setup checks and guidance for users

According to the official docs, after setup you have developers run /status inside Claude Code. The Setting sources line on the Status tab shows Enterprise managed settings, followed by the active sources in parentheses.

There are three main fixes for login problems: switch accounts with /logout followed by /login; run claude update if the enterprise authentication options don't appear; and restart the terminal after updating. If you see "You haven't been added to your organization yet", your seat doesn't include Claude Code access, and an admin needs to update it in the admin console.

FAQ

Do I also configure SSO and SCIM in these managed settings?

No. According to the official docs, SSO, SCIM, and seat assignment are configured on the Claude account side. See the Claude Enterprise admin guide for the steps.

Source: Set up Claude Code for your organization

If we use Bedrock, can we distribute settings from the admin console?

Distribution through the admin console requires a Claude for Teams or Enterprise plan. With Bedrock and similar, the docs say you can do similar remote delivery with the Claude apps gateway, or use file-based or OS-level methods.

Source: Set up Claude Code for your organization

Can developers override managed settings?

With a few exceptions, managed values take precedence over user settings and project settings. You can add to array settings, but you can't remove items set by the managed side. Check the official docs for details on the exceptions.
