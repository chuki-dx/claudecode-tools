Keeping Claude Code from reading .env, and the limits of that setting (verified on Windows)

Published: October 14, 2026 ・ Chuki DX Lab ・ Content is based on the official docs as of writing (October 2026) and results verified on a real machine

Key takeaways

  • Adding Read(./.env) to deny in .claude/settings.json blocked Claude's Read tool and cat .env (verified on Windows 11).
  • On the other hand, opening .env from inside a Python script was not blocked. This isn't a bug; it's behavior documented in the official docs.
  • Use deny as a safety net against accidental reads, and combine it with the practice of not keeping real API keys and similar secrets in your working folder.

Why .env is a concern

Many projects use .env as a file for API keys, connection passwords, and similar values. Claude Code (Anthropic's AI coding agent that runs in the terminal) works by reading files in the working folder, so if that folder contains a .env, its contents may end up in the conversation.

Claude Code can block specific operations through permission rules in the settings file settings.json. Writing "do not read this" in CLAUDE.md (a file of instructions read at startup) is a request to the AI, whereas a permission rule is enforced by Claude Code itself. However, the range it blocks is limited. To check where those limits are, I tested it on my own Windows machine.

How to write the settings

In .claude/settings.json in your working folder, add the following deny rules. This file holds project settings, so if you share it through Git, the same rules apply to everyone working in that folder.

{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Bash(curl *)",
      "Bash(git push *)"
    ]
  }
}

In the official docs, Read(./.env) is given as an example that targets the .env in the current folder. To also cover .env files in lower directories, the docs show the Read(**/.env) form. As of writing, placing a .claudeignore file has no effect, and the docs explain that you should list anything you don't want read in a Read deny rule.

On Windows, paths are converted to a form like /c/Users/… before matching. The official docs say that to target .env files across an entire drive, you write something like //c/**/.env.

What I tried on Windows

At Chuki DX Lab, I tested with the following environment (October 13, 2026).

  • Windows 11、Git for Windows(Git Bash)
  • Claude Code 2.1.296
  • Run claude -p (a mode that makes a single request without opening the interface) with --allowedTools "Read,Bash" to allow reading and command execution, and confirm that the deny rules above still take effect.

In a working folder, I placed a dummy .env containing only test values, and a Python script that just opens and prints that .env. I did not use any real keys. I then asked for four operations.

How to read a run that doesn't stop, and why

As of writing, the official docs describe the scope in which Read and Edit deny rules take effect as follows (summarized).

  • Works on Claude's built-in file tools
  • It works for commands Claude Code recognizes as reading files, such as cat, head, and tail
  • It doesn't cover indirect reads and writes, such as a Python or Node script opening files on its own
  • It also doesn't apply to commands that read files without naming them (for example, running grep -r in that folder).

Command rules work the same way. Bash(curl *) blocks the form curl https://…, but reportedly does not catch calls by path such as /usr/bin/curl, or commands wrapped in sh -c '…'.

In other words, deny is not a wall that blocks reading by any means; it is a net that stops ordinary operations. When you explain this internally, mentioning the difference up front helps you avoid problems later, such as "we configured it, but it was still read."

What to know on Windows

  • How commands run depends on whether Git for Windows is installed: According to the official docs, without Git for Windows, commands run in PowerShell. For PowerShell there are rules in the form PowerShell(Remove-Item *), written the same way as Bash rules. If you use PowerShell, consider rules in that form as well.
  • OS-level blocking (the sandbox) is not available on native Windows: As of writing, the official docs say the sandbox runs on macOS, Linux, and WSL 2, and that to use it on Windows you run Claude Code inside WSL 2.

How to think about internal use

  1. Don't put real secrets in your working folder: Manage API keys and similar credentials outside the folder where you launch Claude Code, and pass them as environment variables only when needed. If they aren't there, there's nothing to be read.
  2. Share deny as a safety net: put .env, folders with secrets, and commands that send data externally in deny, and distribute them as the project's .claude/settings.json. This helps prevent accidentally reading or sending them during everyday work.
  3. If you want to standardize across the organization, consider managed settings: The official docs describe distributing deny rules through managed settings, which users cannot override.
  4. Test with dummy data before rolling out: Place a .env containing only test values, check locally once what gets blocked and what doesn't, and then distribute it.

FAQ

If .env is listed in .gitignore, won't Claude read it?

.gitignore excludes files from Git tracking; it is separate from keeping files away from Claude Code. Put files you don't want to commit in .gitignore, and files you don't want Claude to read in deny.

What should I do if I want to block access via Python as well?

A deny rule won't stop this. The official docs describe the sandbox as the way to block access from all processes at the OS level. On Windows, you use it inside WSL 2. The easiest approach is to not put real values in your working folder.

I wrote a deny rule, but it doesn't seem to take effect

The file location or the way the path is written may be wrong. Run /permissions inside Claude Code to see whether your rules are loaded, and use the Troubleshooting Cheat Sheet to look up the cause by symptom.
