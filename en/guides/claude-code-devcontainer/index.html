Running Claude Code in a dev container: settings and organizational rules

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • When you install Claude Code in a dev container, the commands Claude runs execute inside the container, and file edits are reflected in your local repository.
  • To install, add the feature to devcontainer.json and rebuild. Because a rebuild clears authentication, you need to persist ~/.claude.
  • You can apply organization rules with managed-settings.json, but note that when it is delivered through a Dockerfile, anyone with write access to the repository can change it.

What you can do with a dev container

According to the official docs as of writing (October 2026), a dev container is a definition that lets everyone on a team run the same isolated environment. If you install Claude Code (Anthropic's AI coding agent that runs in the terminal) inside it, the commands Claude runs execute in the container instead of on the host, and edits to project files are reflected in your local repository.

You can connect from editors that support the Dev Containers specification, such as VS Code, GitHub Codespaces, JetBrains IDEs, and Cursor. Unsupported editors, such as plain Vim, are not covered.

The official docs warn that running with --dangerously-skip-permissions does not prevent a malicious project from exfiltrating data inside the container (including the credentials in ~/.claude). They recommend using it only with trusted repositories, monitoring Claude's actions, and not mounting host secrets such as ~/.ssh.

Add Claude Code to a dev container

According to the official docs, the Claude Code Dev Container Feature lets you install Claude Code in any dev container. The steps use VS Code as the example. Save the following in .devcontainer/devcontainer.json, or add a features block to an existing file.

{
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
  "features": {
    "ghcr.io/anthropics/devcontainer-features/claude-code:1.0": {}
  }
}

A version tag like :1.0 at the end pins the Feature's install script, not Claude Code itself. The Feature installs the latest Claude Code, which auto-updates by default inside the container. Replace the image line with your own base image, or delete it if you use a Dockerfile.

  1. Save the content above to devcontainer.json
  2. In the Command Palette, run Dev Containers: Rebuild Container
  3. Run claude in the terminal of the rebuilt container and follow the authentication prompts

If the base image has no Node.js, the feature installs it. If that fails and the build stops with Failed to install Node.js and npm, add "ghcr.io/devcontainers/features/node:1": {} above the Claude Code feature and rebuild. With cloud providers such as Amazon Bedrock, the docs recommend not mounting the host's credentials file and instead passing credentials as environment variables, for example through containerEnv.

A setup that keeps authentication across rebuilds

According to the official docs, by default the container's home is discarded on rebuild, so you have to sign in again each time. Auth tokens and session history live in ~/.claude, but OAuth account data and similar are in a separate file, ~/.claude.json, so mounting a volume alone isn't enough. Mount a named volume at ~/.claude and set CLAUDE_CONFIG_DIR to the same path. The following is an example where remoteUser is node.

"mounts": [
  "source=claude-code-config,target=/home/node/.claude,type=volume"
],
"containerEnv": {
  "CLAUDE_CONFIG_DIR": "/home/node/.claude"
}

Replace /home/node with the home directory of your own remoteUser, and if you already have a containerEnv, add the entry there. To keep volumes separate per project, include ${devcontainerId} in the volume name. In GitHub Codespaces, the data persists across stop and start but is lost on a rebuild, so you need the same setup. To carry credentials across codespaces, save either ANTHROPIC_API_KEY or a CLAUDE_CODE_OAUTH_TOKEN obtained with claude setup-token as a Codespaces secret.

Add your organization's rules

According to the official docs, Claude Code reads /etc/claude-code/managed-settings.json on Linux and applies it with the highest priority in the settings hierarchy. It takes precedence over values in ~/.claude and the project's .claude/, and you copy it in from a Dockerfile as follows.

RUN mkdir -p /etc/claude-code
COPY managed-settings.json /etc/claude-code/managed-settings.json

However, because the Dockerfile is in the repository, anyone with write access can change or delete this step. To make it impossible for engineers to bypass, the docs recommend server-managed settings or distribution through MDM.

Environment variables for the whole container go in containerEnv. The following example disables telemetry and error reporting and turns off auto-updates.

"containerEnv": {
  "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1",
  "DISABLE_AUTOUPDATER": "1"
}

CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC also disables the feature-flag evaluation that Remote Control and similar features depend on, so they won't work in the container. To pin a version, run npm install -g @anthropic-ai/claude-code@X.Y.Z in the Dockerfile instead of using the feature, and set DISABLE_AUTOUPDATER to 1. Define MCP servers at project scope in .mcp.json at the repository root, and you can check them in along with the configuration.

Handling network restrictions and permission prompts

You can limit outbound traffic to only the domains you need. Check the domains on the network requirements page in the official docs. The reference container's init-firewall.sh restricts traffic to allowed destinations only. A firewall inside the container needs extra privileges, so runArgs adds NET_ADMIN and NET_RAW. These aren't required by Claude Code itself, and you can instead rely on your own network controls.

Because the container runs as a non-root user, you can pass --dangerously-skip-permissions for unattended operation. The CLI refuses to start as root, so check that remoteUser is non-root. However, confirmation before tool execution is gone, and Claude can modify files in the bind-mounted workspace, with changes applied directly to the host. Combine this with network restrictions.

If you want fewer prompts while keeping safety checks, auto mode has a classifier that reviews actions before they run. To prohibit this flag itself, set permissions.disableBypassPermissionsMode to "disable" in managed settings. To try it out, the anthropics/claude-code repository includes a reference dev container. It is described as a working example, not a maintained base image.

FAQ

Why do I have to sign in again every time I rebuild?

By default, the container's home directory is discarded on rebuild. If you mount a named volume at ~/.claude and set CLAUDE_CONFIG_DIR to the same path, .claude.json is also written inside the volume. GitHub Codespaces also loses it on rebuild, so the same setup is needed there.

Source: Development containers

If I install managed-settings.json in a Dockerfile, can users no longer change the settings?

The Dockerfile lives in the repository, so anyone with write access can change or delete the steps. If you want rules that can't be bypassed by editing repository files, the official docs point to server-managed settings or distribution via MDM.

Source: Development containers

Is it safe to use --dangerously-skip-permissions in a dev container?

It is not safe. It cannot stop a malicious project from exfiltrating information from inside the container, and changes in the workspace are reflected on the host. Use it only with trusted repositories, and combine it with network restrictions. There is also a setting that prohibits the flag itself.
