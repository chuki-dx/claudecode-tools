How Claude Code works: the agent loop and what Claude can touch

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • According to the official docs, Claude Code (an AI coding agent from Anthropic that runs in the terminal) works by repeating three steps: gather context, take action, and verify results. You can interrupt it at any time.
  • Claude Code can reach the files in the directory where you run it, any command you can run in the terminal, the state of git, CLAUDE.md, and similar. Before you try it, decide which directory you will launch it from.
  • You can roll back file edits with checkpoints, but you can't undo operations on external systems such as databases, APIs, and deployments. Control these with permission modes and permission rules.

The agent loop: gather context, act, and verify

According to the official docs, Claude Code is an agentic assistant that runs in the terminal. It excels at coding, but it can also help with anything you can do on the command line, such as writing documents, building, searching files, and research.

When you hand over a task, Claude works in three phases: gather context, take action, and verify results. The phases blend together, and Claude uses tools throughout, whether searching, editing, or running tests.

The loop adapts to your request. A question about the codebase may need only context gathering, while a bug fix cycles through all three phases repeatedly. Claude decides the next step based on what it learned in the previous one. You are part of the loop too: you can interrupt at any point to redirect it or supply more context.

The loop consists of a model that reasons and tools that actually act. Claude Code is the surrounding layer that gives the model its tools and manages the context the model sees. The official docs call it an agentic harness (the layer that handles tools and context around the model). You can choose from several models and switch with /model.

Tools: what Claude can actually do

The official docs explain that tools are what let Claude Code act as an agent. Without tools it can only reply with text, but with them it can read, edit, run commands, search the web, and interact with external services. The built-in tools fall into five broad categories.

  • File operations: reading files, editing code, creating new files, renaming and organizing
  • Search: finding files by pattern, searching contents with regular expressions, and exploring a codebase
  • Execution: shell commands, starting servers, tests, git
  • Web: web search, fetching documentation, and investigating error messages
  • Code intelligence: checking type errors and warnings after edits, jumping to definitions, and finding references (requires code intelligence plugins)

If you ask it to "fix the failing tests," it may run the tests, read the error output, search for and read related files, edit them, and run the tests again to confirm. The result of each tool becomes input for the next step.

As extensions, you can add knowledge with skills, connect to external services with MCP, automate workflows with hooks, and delegate tasks to subagents. All of them are layers that sit on top of the basic loop.

What Claude can touch: files, commands, git, and CLAUDE.md

According to the official docs, when you run claude in a directory, it gets access to the following.

  • Project: files in the directory and its subdirectories. Files elsewhere, if you grant permission
  • Terminal: build tools, git, package managers, scripts, and anything else you can do from the command line
  • Git state: the current branch, uncommitted changes, and recent commit history
  • CLAUDE.md: a markdown file where you write project-specific instructions and conventions. In repositories that have an AGENTS.md for other coding agents, Claude Code can read that instead
  • Auto memory: learnings saved automatically while you work. Whichever comes first, the first 200 lines or 25KB of MEMORY.md, is loaded at the start of a session.
  • Extensions you configured: MCP servers, skills, subagents, Claude in Chrome

Claude looks at the whole project, so it can work across files. If you ask it to "fix the authentication bug," it finds the related files, reads several of them, edits them together, verifies with tests, and even commits if you ask. This differs from an inline code assistant that only sees the current file.

Sessions and context: what Claude remembers and what it forgets

According to the official docs, conversations are stored locally. Each message, tool use, and result is written as a plain-text JSONL file under ~/.claude/projects/. This is what makes rewind, resume, and branching possible. For storage location, retention period, and how to delete data, check the official docs.

Sessions are independent, and a new session starts without the previous conversation history. What carries over is auto memory and the contents of CLAUDE.md. claude --continue or claude --resume resumes with the same session ID, while --fork-session or /branch copies the history into a new session ID.

The context window (the working space Claude can hold at once) contains the conversation history, file contents, command output, CLAUDE.md, auto memory, loaded skills, and system instructions. When it fills up, it is compacted automatically, and instructions from early in the conversation may be lost. Put rules you want followed in CLAUDE.md, and check usage with /context.

There are three places to run it: local (your own machine, the default), cloud (Anthropic-managed VMs, or self-hosted environments run by your organization), and Remote Control (runs on your machine and is operated from a browser). The loop is the same no matter which interface you use.

Safety: checkpoints and permission modes

The official docs list two safety mechanisms: checkpoints that let you undo file changes, and permissions that decide what Claude can do without asking. A snapshot is taken before each edit, and you can roll back by pressing Esc twice or asking Claude to rewind. Checkpoints are separate from git and cover file changes only. Operations on external systems such as databases, APIs, and deployments cannot be undone.

Press Shift+Tab to switch permission modes.

  • Auto: A classifier reviews many actions in the background and blocks risky ones without asking for confirmation. In Claude Code v2.1.283 and later, it is a built-in starting mode in interactive terminals and VS Code sessions; in earlier versions, it is limited to Pro, Max, and Team plans
  • Manual: asks for confirmation before file edits and shell commands
  • Accept edits: Runs file edits and common filesystem commands such as mkdir and mv without asking, and asks about other commands
  • Plan: researches and proposes a plan without editing source files

You can also allow trusted commands such as npm test and git status in .claude/settings.json. Settings can be scoped from organization-wide policy down to personal settings. See Permissions in the official docs for details.

FAQ

What is the "agent loop" in Claude Code?

According to the official docs, it works by repeating three phases while using tools: gathering context, taking action, and verifying results. The phases blend together, and how the loop runs varies with the request. You can interrupt at any point.

Source: How Claude Code works

What do I do if I want to change direction midway?

According to the official docs, Esc stops Claude, cancels any running tool call, and waits for your next instruction. If you type a correction without stopping and press Enter, the message is queued. It is read in the same turn after the running tool call finishes, and it adjusts the work before the next step.

Source: How Claude Code works

Can I undo changes Claude made?

File edits can be undone using snapshots taken before each edit, by pressing Esc twice or asking Claude. However, this covers file changes only, and restoring skips symlinked and hard-linked files. Operations on external systems such as databases, APIs, and deployments can't be checkpointed, so control them with permission modes and permission rules.
