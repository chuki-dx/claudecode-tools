The basics of Claude Code permissions (deny/ask/allow), and what they do and don't cover

Published: October 14, 2026 ・ Chuki DX Lab ・ Content is based on the official docs as of writing (October 2026)

Key takeaways

  • Permission rules come in three types: deny (block), ask (confirm every time), and allow (permit without confirmation). They are evaluated in the order deny → ask → allow. An operation that matches deny can't be used even if you also list it in allow.
  • deny blocks Claude's read tools and "ordinary" operations such as cat and curl. However, it does not block a script that opens files on its own.
  • Use deny as a safety net against accidents, and combine it with a practice of never keeping real secrets in your working folder.

What permissions settings are

Claude Code (an AI coding agent from Anthropic that runs in the terminal) checks the permission rules in your settings file every time it performs an operation, such as reading or writing a file or running a command. You write the rules under permissions in settings.json, which is in JSON format.

There are three types of rules:

  • deny: block the operation
  • ask: Asks the user for confirmation every time before running
  • allow: Allow execution without asking for confirmation

The official docs explain that rules are evaluated in the order deny, ask, allow, and the first match decides the result. For example, if you set Bash(aws *) to deny, the command is still blocked even if you add the more specific Bash(aws s3 ls) to allow. Keep in mind that you can't use allow to create an exception to a deny, and you won't get stuck when building your rules.

Writing "don't read .env" in CLAUDE.md (the instruction file Claude Code reads at startup) is a request to the AI. A permission rule, by contrast, is enforced by Claude Code itself, which blocks the operation. As a rule, put anything you need enforced in permission rules, not in prose.

Where settings files live and their precedence

The scope of a settings file depends on where you put it. Here are the four that corporate IT should know.

Where to put itScope and when to use it
.claude/settings.json (inside the working folder)Everyone who uses that folder. Sharing it through Git lets you distribute the same rules
.claude/settings.local.jsonOnly for you, only in that folder: write personal preferences
~/.claude/settings.jsonAll projects you use
Managed settings (for example, C:\Program Files\ClaudeCode\managed-settings.json on Windows)All users of that PC. Users cannot override it

When the same item appears in multiple places, precedence is: managed settings → command line → settings.local.json → project settings.json → user settings.json. For a company-wide rollout, a practical order is to start with the project's .claude/settings.json and consider managed settings only after the rules you want to enforce for everyone have settled.

How to write rules

Rules are written in the form "tool name (target)". Reading a file is Read(path), and a command is Bash(command *). Here is a minimal example that blocks reading .env, stops outbound sends with curl, and forbids git push.

{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Bash(curl *)",
      "Bash(git push *)"
    ]
  }
}

If you also don't want Claude to read the folder that holds real data, use ** to cover everything inside it, as in Read(./data/raw/**). After writing the rule, run /permissions in Claude Code to confirm the rule was loaded.

Operations blocked by deny

At Chuki DX Lab, I tried the settings above (October 2026) on Windows 11 with Git for Windows and Claude Code 2.1.296, in a folder containing a dummy .env (with test values only). The results are as follows.

What you asked forResult
Read .env with Claude's read toolStopped
Run cat .envStopped
Access external sites with curlStopped
Opening and printing .env inside a Python scriptIt was able to read the file

Operations that deny does not stop

The last line is not a bug; it behaves as the official docs specify. As of writing, the official docs describe Read and Edit deny rules as follows (summarized).

  • Works on Claude's built-in file tools
  • It works for commands Claude Code recognizes as reading files, such as cat, head, and tail
  • It doesn't cover indirect reads and writes, such as a Python or Node script opening files on its own

Command rules work the same way. Bash(curl *) blocks the form curl https://…, but it reportedly does not catch calls by path such as /usr/bin/curl or calls wrapped in sh -c '…'. In other words, deny is not a wall that prevents reading by any means; it is a net that stops ordinary operations.

If allow doesn't seem to work

An allow rule in a project's .claude/settings.json is not used until someone accepts the workspace trust prompt for that folder. Deny and ask rules restrict behavior, so they take effect regardless of trust. If a command you put in allow still prompts for confirmation after you distribute the file, have the user start claude once in an interactive session and accept the trust prompt.

How to think about internal use

  1. Don't put real secrets in the working folder: manage API keys and the like outside the folder. Not placing them there at all is more reliable than protecting them with deny.
  2. Share deny as a safety net: Put .env, secrets/, folders with real data, and commands that send data externally into deny, and distribute them through Git as project settings.
  3. If you need a hard stop, use a different mechanism: The official docs describe a sandbox that blocks access at the OS level. As of writing, it is not available on native Windows; it is said to work when you run Claude Code inside WSL 2.
  4. Test with dummy data before distributing: place a file containing test values, confirm locally once that it can't be read or sent, and then distribute.

FAQ

What happens if I write the same rule in both deny and ask?

deny is evaluated first, so the action is blocked. If you only want a confirmation prompt, write the rule only in ask.

Are files listed in .gitignore not read?

.gitignore tells Git which files to leave out of version control, which is separate from keeping files away from Claude Code. Put anything you don't want Claude Code to read in deny as well, and anything you don't want committed in .gitignore as well.

I wrote a rule, but it doesn't seem to take effect

The file location or path syntax may be wrong. Use /permissions to check whether the rules were loaded, and confirm you placed the file at .claude/settings.json in your working folder.
