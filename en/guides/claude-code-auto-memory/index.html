Claude Code auto memory: where it's stored, how to turn it off, and how to check it

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • Auto memory is a mechanism where Claude keeps notes for itself. It is on by default in local sessions, and it serves a different role from the CLAUDE.md that people write.
  • Memory is stored in ~/.claude/projects/<project>/memory/ and is local to the machine. The contents are plain Markdown, so you can view, edit, and delete them from /memory.
  • To turn it off, use the /memory toggle, autoMemoryEnabled, or the environment variable CLAUDE_CODE_DISABLE_AUTO_MEMORY=1. Note that some sessions can't be switched back on.

What auto memory is: how it differs from CLAUDE.md

According to the official docs as of writing (October 2026), Claude Code (an AI coding agent from Anthropic that runs in the terminal) has two complementary memory mechanisms, both loaded at the start of a conversation. One is CLAUDE.md, a file where people write instructions and rules for Claude. The other is auto memory.

Auto memory is a mechanism where Claude accumulates learnings and patterns across sessions without you writing anything. CLAUDE.md is meant for coding conventions and workflows that you write, while auto memory is meant for your preferences, your corrections to Claude, and project background that can't be read from the code. The scope also differs: auto memory is per repository and shared across worktrees.

Note that for both, Claude treats them as context rather than enforced settings. If you need to reliably block an operation, the official docs direct you to use a PreToolUse hook.

What is stored and what is not

While working, Claude saves four types of notes for itself, and the type is recorded in the type field of the note file's frontmatter.

  • user: the user's role, expertise, and working preferences
  • feedback: Corrections to Claude, and approaches you've confirmed
  • project: Ongoing work, deadlines, and decisions that can't be derived from the code or git history
  • reference: Where to find information outside the project, such as issue trackers and dashboards

It does not save things that can be derived from the codebase, such as architecture, file paths, or debugging fixes, or anything already in CLAUDE.md. It also does not save every session; it decides based on whether the information will be useful in future conversations.

If you ask Claude to remember something, such as "always use pnpm, not npm," it is saved to auto memory. To put it in CLAUDE.md, ask it to "add this to CLAUDE.md" or edit the file via /memory.

Storage locations and folder structure

Each project gets a directory named ~/.claude/projects/<project>/memory/. Because <project> is derived from the git repository, worktrees and subdirectories of the same repository share one auto memory. Outside a git repository, the project root is used.

~/.claude/projects/<project>/memory/
├── MEMORY.md           # Index, one line per memory, loaded into every session
├── user_role.md        # One memory
├── feedback_testing.md # One memory
└── ...                 # Any other topic files Claude creates

MEMORY.md is an index, with one line per memory. The memory contents themselves go into separate files by topic. To change where they are stored, set autoMemoryDirectory in settings.json.

{
  "autoMemoryDirectory": "~/my-custom-memory-dir"
}

The value must be a full path or start with ~/. When it's written in a project settings file, it follows the same workspace trust rules as hooks in settings files. Also, while permissions.blockReadsOutsideWorkingDirectories is on, auto memory is neither loaded from nor saved to a directory chosen by a repository-level settings file.

How to turn it on and off

Auto memory is on by default in local sessions. Outside Claude Tag sessions, sessions in self-hosted environments run with it off by default.

If you open /memory in a session and use the auto memory toggle, autoMemoryEnabled is saved to the user settings file ~/.claude/settings.json. To turn it off for just one project, add the following to that project's settings.

{
  "autoMemoryEnabled": false
}

To turn it off with an environment variable, set CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.

Sessions that can't be turned back on

In the next session, you can turn it off with the toggle, but you can't turn it back on.

  • Background sessions
  • A session launched by another Claude Code session (for example, when Claude runs claude through the Bash tool)

Meanwhile, the toggle shows off · can't be turned on here; use a session started outside Claude Code. To turn it back on, run claude directly in a terminal and use the /memory toggle in that session.

How loading works and things to watch for

At the start of a conversation, MEMORY.md is loaded up to the first 200 lines or the first 25KB, whichever comes first; anything beyond that is not loaded. Claude moves details into topic files to keep the index short. Topic files such as user_role.md are not loaded at startup; Claude reads them when needed.

If you exceed the limit, the write itself still succeeds, but Claude Code returns an error asking you to rewrite the index, because everything past the limit is dropped on the next load. This limit applies only to MEMORY.md. The CLAUDE.md loaded at startup is read in full as long as it is 4 MiB or less (CLAUDE.md files in subdirectories and path-scoped rules have separate, smaller per-file limits).

  • Files are not shared across machines or across cloud environments.
  • Session transcripts are deleted after the retention period set by cleanupPeriodDays, but memory files are not affected. They stay until you or Claude edit or delete them.
  • Auto memory from the main conversation is not loaded into subagents (forks are the exception). A subagent's own auto memory lives in a separate directory.

Reviewing and editing the contents

Auto memory files are plain Markdown, and you can edit or delete them at any time. Running /memory lists locations such as CLAUDE.md and CLAUDE.local.md, and gives you options to toggle auto memory on or off and to open the auto memory folder.

GUI editors (such as VS Code) open in a separate window, while terminal editors such as Vim occupy the terminal until you exit. When you see "Saved 2 memories" or "Recalled 2 memories," Claude has updated or loaded ~/.claude/projects/<project>/memory/.

Before distributing within the company, it's a good idea to check what gets saved using this method. For points not covered in the source, such as distributing settings to the whole organization, check the official docs.

FAQ

Is auto memory shared with other PCs or team members?

According to the official docs, auto memory is machine-local, and its files are not shared across machines or cloud environments. It is shared only among worktrees and subdirectories within the same git repository.

Source: How Claude remembers your project

I turned auto memory off and can't turn it back on.

In background sessions and sessions started by another Claude Code session, the toggle can only be turned off, not back on. Run claude directly in a terminal and use the /memory toggle in that session.

Source: How Claude remembers your project

I can't tell what auto memory has saved. How do I check?

Run /memory and select the auto memory folder to see what Claude has saved. It's all plain Markdown, so you can read, edit, or delete it.
