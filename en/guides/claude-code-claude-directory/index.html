The structure of Claude Code's .claude folder: what to write in which file

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • According to the official docs, Claude Code (Anthropic's AI coding agent that runs in the terminal) settings files are split into project settings placed in the repository's .claude/ and global settings placed in ~/.claude/ that apply to all projects.
  • If you're unsure where to write something, choose by what you want to do. Conventions go in CLAUDE.md; permissions, hooks, and environment variables go in settings.json; personal overrides go in settings.local.json.
  • With a few exceptions, your organization's managed settings take precedence over individual settings files and --settings. If a setting isn't taking effect, check the override order and the official debugging steps.

Where to put the .claude folder: project-level vs. global

The official docs as of writing (October 2026) explain that project files go under .claude/ in the repository. The exceptions are CLAUDE.md, .mcp.json, and .worktreeinclude, which go in the repository root. Global files go in ~/.claude/ and apply to all projects.

Depending on the file, it can live in both the project and global locations, only in the project, or only globally. For example, .mcp.json and settings.local.json are project-only, while keybindings.json and themes/*.json are global-only.

In the table, the Commit column has a ✓ for files such as CLAUDE.md, settings.json, and skills/<name>/SKILL.md. settings.local.json has no ✓; the docs say it is gitignored when Claude Code saves settings there.

Choose which file to edit based on what you want to change

The official docs include a table showing where to edit for each kind of change. The main ones are as follows.

  • Give project context and conventions: CLAUDE.md (project or global)
  • Allowing or blocking tool calls: permissions or hooks in settings.json
  • Run scripts before and after tool calls: hooks in settings.json
  • Set session environment variables: env in settings.json
  • Keep personal overrides out of git: settings.local.json (project only)
  • Add prompts or features you invoke with /name: skills/<name>/SKILL.md
  • Define a subagent with its own dedicated tools: agents/*.md
  • Coordinate many subagents from a script: workflows/*.js
  • Connect external tools with MCP: .mcp.json (project only)
  • Change how responses are formatted: output-styles/*.md

settings.json is a file that holds permissions, hooks, environment variables, and model defaults together. It helps to keep them organized by putting team-shared settings in settings.json and personal overrides in settings.local.json.

What the other files not in the table above do

Some files in the file list don't appear in the editing-target table. The official docs explain it as follows.

  • rules/*.md: Topic-specific instructions, which can also be limited to target paths (project and global)
  • commands/*.md: a single-file prompt that works the same way as skills
  • .worktreeinclude: specifies gitignored files to copy into new worktrees (project only)
  • agent-memory/<name>/: persistent memory for a subagent
  • ~/.claude.json: holds app state, account information, UI toggles, and your personal MCP servers (global only)
  • projects/<project>/memory/: notes Claude keeps for itself across sessions (auto memory). Global only.
  • keybindings.json: keyboard shortcut settings (global only)
  • themes/*.json: color theme settings (global only)

Files and fields you configure in frontmatter

Skills, commands, subagents, output styles, and rules read their settings from the YAML frontmatter (the header section that holds settings) at the top of the file. The fields each one accepts differ from file to file.

  • skills/<name>/SKILL.md: name, description, allowed-tools, model, paths, and more
  • commands/*.md: the skills fields minus name and paths
  • agents/*.md: name, description, tools, permissionMode, and so on
  • output-styles/*.md:name、description、keep-coding-instructions、force-for-plugin
  • rules/*.md:paths

For agents distributed through plugins, only some of the subagent fields are valid. Check each reference for the meaning of every field.

Files outside .claude, and overriding settings

According to the official docs, the following files are stored in a different location.

  • managed-settings.json: Placed at the system level, with a location that varies by OS. These are settings enforced by the organization, and your own settings files or --settings values cannot override them, with limited exceptions
  • CLAUDE.local.md: Your personal preferences for that project, placed in the project root. It is loaded together with CLAUDE.md. Create it manually and add it to .gitignore
  • AGENTS.md: You can place it in the project root, in .claude/, or in any directory. It can be loaded in place of CLAUDE.md
  • Installed plugins: stored in ~/.claude/plugins and managed with the claude plugin command

~/.claude also holds data that Claude Code writes while you work: conversation transcripts, prompt history, file snapshots, caches, and logs.

Overrides also need attention. Your organization's managed settings take precedence over all settings files and --settings values, except for the exceptions listed in Settings precedence. CLI flags such as --permission-mode and --settings override settings.json for that session. Some environment variables take precedence over the corresponding settings, but this differs by variable, so check the environment variable reference. If a setting isn't taking effect, the official Debug your configuration page has diagnostic commands and a symptom-based cheat sheet.

FAQ

Where should I put personal settings if I don't want to share them with the team?

According to the official docs, personal setting overrides go in settings.local.json (project only). Personal instruction preferences go in CLAUDE.local.md at the project root. You create this file manually and add it to .gitignore.

Source: Explore the .claude directory

Can I enforce settings across the organization?

The official docs explain that managed settings distributed by an organization take precedence over all settings files and the --settings value, with a limited set of exceptions. The location of managed-settings.json differs by OS, so check the official managed settings page for where to put it.

Source: Explore the .claude directory

What should I check when something I wrote in settings.json has no effect?

Your organization's managed settings, CLI flags, or some environment variables may be overriding it. The full order is in the official settings precedence page, and the commands for checking are in Debug your configuration.

Source: Explore the .claude directory
