How to resume a previous conversation in Claude Code: --continue, --resume, and naming sessions

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • Conversations in Claude Code (an AI coding agent from Anthropic that runs in the terminal) are saved locally per project. You can resume the most recent one with claude --continue, or pick one from a list with claude --resume.
  • If you run a lot of work in parallel, name sessions with claude -n auth-refactor or /rename auth-refactor so you can return directly with claude --resume <name>. Even without a name, the generated title can be used to resume.
  • Some launch options are not restored on resume, and the permission mode of a conversation that ended in bypassPermissions is not restored either. Check what gets restored before you roll this out company-wide.

Entry points for resuming a previous conversation

According to the official docs, a session is a saved conversation tied to a project directory. It keeps being saved as you work, so you can return to it after exiting or after /clear. This article covers the CLI; the desktop app, claude.ai/code, and the VS Code extension each have their own separate session lists.

  • claude --continue: Reopens the most recent session in the current directory
  • claude --resume: Opens the session picker (a screen where you choose from a list)
  • claude --resume <name>: Resumes a named session directly
  • claude --resume <transcript-path>: Resumes from a .jsonl transcript file, specified by its full path.
  • claude --from-pr <number>: Opens a picker filtered to sessions linked to that pull request.
  • /resume: switch to a different session from within a running session

This is a summary based on the official docs as of writing (October 2026), not on my own testing. Some behavior changes between versions, so check the latest official docs before you adopt it.

Source: Manage sessions

Name a session and resume it

The official docs recommend giving sessions clear names, especially when you run multiple tasks in parallel. A name makes a session easier to find in the picker and can also be used to resume it.

  • At startup: claude -n auth-refactor
  • During a session: /rename auth-refactor (the name also appears in the prompt bar)
  • From the picker: select a session and press Ctrl+R
  • When you approve a plan in plan mode: if no name is set, a title based on the plan is added automatically

After you name a session, you can return to it with claude --resume <name> or /resume <name>. On an exact match, the session resumes directly, even if it lives in a different worktree (another working directory of the same repository). If the name matches multiple sessions, claude --resume <name> opens the picker with the name as the search term, while /resume <name> returns an error. In that case, run /resume with no argument to open the picker.

A session you haven't named gets a default display name (something like my-app-3f) and a generated title that summarizes the first prompt. Only the generated title works for resuming; passing the default display name won't find the session.

Source: Manage sessions

How to use the session picker and what it can search

Run claude --resume with no arguments, or run /resume during a session, to open the picker. The main controls are as follows.

  • ↑ / ↓ to move, Enter to resume, Space to preview the contents
  • Search with / and similar. Paste a pull request URL to find the session that created it
  • Ctrl+A shows all projects on this machine, Ctrl+W shows all worktrees in the repository, and Ctrl+B filters to the current git branch

By default, it shows sessions from the current worktree, plus sessions started in other locations where you added the current directory with /add-dir.

Here is a caveat if a session doesn't show up in the list. A session whose first prompt was /loop appears neither in the picker nor with claude --continue. The same is true of sessions created with claude -p or the Agent SDK, but you can resume them by passing the session ID to claude --resume <session-id>.

What is restored on resume and what you need to provide again

According to the official docs, when you load a conversation from a transcript, the following state is restored in addition to the conversation history, including tool calls and results.

  • Model: it continues with the model you were using (for exceptions, check the official model configuration page)
  • Agent: a session started with --agent or similar continues as that agent
  • Permission mode: if you use claude --continue or similar in the terminal without -p, the permission mode from when the session ended is restored. You can override it with --permission-mode or similar
  • Scheduled tasks: those that haven't expired are restored, but background Bash and monitor tasks are not

Some things are not restored. If a session depended on --mcp-config, --settings, --plugin-dir, --fallback-model, or --add-dir, pass them again when you resume. Directories you added mid-session with /add-dir are not restored either. Configuration files such as settings.json are re-read at startup, so you don't need to pass them again.

For permission modes: if a session that ended in bypassPermissions is resumed in the terminal, that mode is not restored, and the session starts in the same mode as a new session. If it ended in plan mode, resuming in the terminal returns you to plan mode (except when you add --fork-session, or when a deny rule has removed the ExitPlanMode tool).

Resuming a conversation left idle for a long time

On a Pro or Max plan, if you resume a session that has been idle for more than about an hour and exceeds 100,000 tokens, a dialog appears before your first message. Resume from summary runs /compact and carries the summary forward. Later costs go down, but anything the summary left out disappears from Claude's context. Resume full session as-is loads the conversation unchanged. If you choose Don't ask me again, the dialog no longer appears on future resumes.

Source: Manage sessions

Notes on branching and where sessions are saved

To keep the original conversation and try a different approach, use /branch during the session, or combine it with --fork-session on the command line as shown below.

claude --continue --fork-session

If you resume the same session in two terminals without forking it, messages from both get mixed into a single record.

Transcripts are saved by default to ~/.claude/projects/<project>/<session-id>.jsonl and kept for 30 days. You can change this with cleanupPeriodDays in settings.json. The transcript format is an internal detail of Claude Code and changes between versions, so scripts that parse it directly may break. To keep a human-readable record, use /export. To delete transcripts sooner, there is claude purge.

Source: Manage sessions

FAQ

How do I quickly resume my most recent conversation?

Use claude --continue. It reopens the most recent session in the current directory. Sessions whose first prompt was /loop, and sessions created with claude -p or the Agent SDK, are not included. It also won't open a background session that is still running; it prints a message and exits.

Source: Manage sessions

Can I resume a conversation that I haven't named?

Yes. Pick it in the picker, or pass the generated title to claude --resume or /resume. The default display name (something like my-app-3f) can't be used to resume. Also, claude -p run directly from a shell or script doesn't get a title.

Source: Manage sessions

Can I resume a conversation that I started in a different directory?

You can run claude --resume <session-id> from any directory. It first searches the current project's directory and its worktrees, then other projects on this machine. For other projects, it resolves only when exactly one project has a record of the session. If nothing matches, it shows No conversation found with session ID: <session-id>.

Source: Manage sessions
