How to restrict MCP in Claude Code within your company: allow/deny lists and managed-mcp.json

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • According to the official docs, MCP servers in Claude Code (an AI coding agent from Anthropic that runs in the terminal) can be restricted using several patterns, such as disabling them entirely, distributing a fixed set, allowing only approved ones, or deny-only.
  • To distribute the same fixed servers to everyone, use managed-mcp.json. To restrict what users can add themselves, use allowedMcpServers and deniedMcpServers.
  • To make an allowlist that users cannot widen, put allowedMcpServers and allowManagedMcpServersOnly: true together in managed settings. serverName does not work as a security measure.

First decide: how far to restrict

This article is based on the official docs as of writing (October 2026). There are three mechanisms for restricting MCP servers (the servers you add to Claude Code as connection targets). managed-mcp.json distributes a fixed set of servers, managedMcpServers has the company provide servers in addition to those users add, and allowedMcpServers/deniedMcpServers narrow down what users have configured.

The official docs list the following restriction patterns.

  • Disable everything: a managed-mcp.json with an empty server definition. The exception is certain servers that are loaded under exclusive control.
  • Fixed distribution: a managed-mcp.json that lists the servers you want. Everyone uses the same servers and can't add their own.
  • Provided servers: managedMcpServers. It distributes the remote servers your company lists, and users' own servers remain as well.
  • Approved catalog: allowedMcpServers and allowManagedMcpServersOnly: true. Anything not approved is blocked.
  • Plugin servers only: include mcp in the strictPluginOnlyCustomization list.
  • Loose allowlist: allowedMcpServers without allowManagedMcpServersOnly. Users can extend it in their own settings.
  • Deny list only: deniedMcpServers. It blocks only the problematic servers and allows the rest.

Claude Code has no built-in MCP server registry that users can browse and install from. With an approved-catalog approach, you either share the approved list and the claude mcp add commands somewhere users can easily find them, such as an internal wiki, or distribute them as plugins through a managed plugin marketplace.

Source: Control MCP server access for your organization

Distributing fixed servers with managed-mcp.json

According to the settings reference in the official docs, managed-mcp.json goes in one of these system paths: /Library/Application Support/ClaudeCode/, /etc/claude-code/, or C:\Program Files\ClaudeCode\. Distribute it through MDM, GPO, fleet management, or a process with administrator privileges. It can't be set through server-managed settings.

After distribution, when a user runs claude mcp add, a message says it can't be added. Also, when a user who can use Claude in Chrome runs claude --chrome, it exits at startup. To allow it, set allowClaudeInChromeWithManagedMcp in the device-side managed settings (only MDM profiles, the HKLM registry, and managed-settings.json are effective).

Configuring the allow and deny lists

The allowlist and denylist are filters that narrow down which servers are allowed to load. They are not a registry, so a server is only subject to them once it has been added by a user, a plugin, or the organization.

Fix the allow list on the admin side

Put allowedMcpServers and allowManagedMcpServersOnly: true together in managed settings, such as server-managed settings or a distributed managed-settings.json. Reading the lock and the allowlist across multiple managed sources requires Claude Code v2.1.273 or later.

{
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [
    { "serverUrl": "https://api.githubcopilot.com/*" },
    { "serverUrl": "https://*.internal.example.com/*" }
  ]
}

While this is true, the user, project, and local allowlists are ignored. Denylists are merged across all scopes, so users can still block things for themselves.

Without allowManagedMcpServersOnly, allowlists are merged across all scopes, and users can extend them in their own ~/.claude/settings.json. Note that allowManagedPermissionRulesOnly locks down only permission rules and does not enforce the MCP allowlist.

Unset vs. an empty array

  • If allowedMcpServers is not set, all servers are allowed. If it is an empty array [], none are allowed (except servers that skip the allowlist check). If it has entries, only matching servers are allowed.
  • If deniedMcpServers is unset or an empty array, nothing is blocked. If it has entries, matching servers are blocked regardless of other settings.

How to write entries and points to note when matching

Write each entry using exactly one of the following keys.

  • serverUrl: For HTTP and SSE remote servers. Write the URL as an exact match or with a * wildcard.
  • serverCommand: For stdio servers. The command and arguments must match exactly, including order, and env is not compared.
  • serverName: matches only the label the user gave exactly; wildcards are not supported.

The official docs warn that serverName is not a security control. The name is a label chosen by the user, and any server can be named github. To control which servers actually run, use serverCommand or serverUrl.

Pay attention to URL ports as well. If you write the full hostname and omit the port, only the default port applies (443 for https, 80 for http); if the hostname contains *, all ports are covered. The same goes for deny lists: https://staging.example.com/* does not block https://staging.example.com:8443/api.

If the allowlist contains even one serverUrl, remote servers must match by URL, and matching by serverName applies only when there is no serverUrl. The same goes for stdio with serverCommand. The official docs recommend writing entries you rely on for enforcement with literal URLs and commands.

Source: Control MCP server access for your organization

Servers that don't pass the allowlist, and what users see

Some servers skip the allowlist check: your organization's own servers (everything in managedMcpServers, plus managed-mcp.json entries that don't use ${VAR} expansion outside env), built-in servers such as Claude in Chrome and the ide server, and the Slack tools in Claude Tag sessions. The denylist applies regardless of where a server comes from, except for in-process servers with type: "sdk".

Also check in advance how this looks to users. When a previously configured server is blocked by policy, it disappears from /mcp and claude mcp list. Because the reason isn't shown to users, you need to tell them what is blocked when you roll out a new restriction.

FAQ

Can users expand the allowlist themselves?

It is possible if you don't set allowManagedMcpServersOnly. Allowlists are merged across all scopes, and users can extend them in their own ~/.claude/settings.json. If you put allowedMcpServers and allowManagedMcpServersOnly: true in managed settings, the user, project, and local allowlists are ignored.

Source: Control MCP server access for your organization

Is it OK to manage allow and deny by serverName alone?

According to the official docs, serverName is not a security measure. The name is a label chosen by the user, not the actual server. To control which servers actually run, add serverCommand or serverUrl entries.

Source: Control MCP server access for your organization

If I distribute managed-mcp.json, can users no longer add MCP servers?

According to the official docs, in the fixed-distribution pattern everyone uses the same servers and no others can be added. Running claude mcp add shows an error saying that the enterprise MCP configuration is active and has exclusive control.
