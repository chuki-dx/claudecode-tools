How to check when your Claude Code settings aren't taking effect

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • When settings in Claude Code (Anthropic's AI coding agent that runs in the terminal) don't take effect, first check what was actually loaded with /context.
  • The cause is often said to be one of these: it was not loaded, it was loaded from a different location, or it was overridden by another setting. Check in order: precedence, the hook matcher, MCP approval, and so on.
  • If you have no idea what's wrong, isolate whether the problem persists by running claude --safe-mode, or by starting in an empty directory with a clean settings directory.

First, check what was loaded

According to the official docs, when instructions are ignored or a feature you configured doesn't appear, the cause is most often one of these: the file wasn't loaded, it was loaded from a different location than you expected, or it was overridden by another file.

Start by running /context. It breaks down what is taking up the context window (the amount of information the AI can reference at once) in the current session, split into the system prompt, MCP tools, memory files, skills, conversation messages, and so on. You can check whether your CLAUDE.md and skill descriptions are loaded. To look closer at a specific item, use the commands below.

  • /memory: Shows where the memory files are located.
  • /skills: shows the available skills.
  • /hooks: Shows the active hook configuration.
  • /mcp: Shows MCP servers and their connection status.
  • /permissions: Shows the active allow and deny rules.
  • /doctor: checks for problems such as invalid settings files and suggests fixes.
  • /status: Shows where the active settings were loaded from and whether managed settings are present.

A CLAUDE.md in a subdirectory is loaded only when needed, so it does not appear in the /context breakdown. When a file is loaded but not followed, the usual causes are said to be vague instructions, contradictions between files, or an overly long file. For things that must never happen, use permissions or hooks instead of CLAUDE.md.

Check settings precedence and where they are stored

The official docs explain that settings are merged across the managed, user, project, and local scopes. If managed settings exist, they are applied first; otherwise the nearest scope wins, in the order local, project, user. Command-line flags and environment variables act as one more overriding layer.

You can diagnose an invalid settings file read-only by running claude doctor in a terminal. Proposing a fix and confirming it before applying is done with /doctor inside a session.

  • Writing permissions, hooks, or env in ~/.claude.json has no effect. That file is for app state; put these in ~/.claude/settings.json.
  • settings.local.json overrides settings.json, and both override ~/.claude/settings.json.

When hooks don't appear or don't run

/hooks lists the hooks in the current session (processes that run automatically, for example before or after a tool runs). If you defined one and it doesn't appear, it hasn't been loaded.

  • Writing them in a standalone file: hooks go under the "hooks" key in a settings file. Only plugins read a separate hooks/hooks.json file.
  • matcher is an array: it is shown as an invalid setting, and if it is under PreToolUse or PermissionRequest, the other hooks in that file are not loaded either.

If it appears but doesn't run, check the matcher.

  • To match multiple tools, join them with | in a single string, for example "Edit|Write".
  • Comma (,) separators have the same meaning from v2.1.191 onward. Before that they don't match, so use |.
  • Tool names are case-sensitive. They start with a capital letter, as in Bash, Edit, Write, and Read. If you misspell one, it matches nothing and fails silently.

If you can't find the cause, start with claude --debug and trigger a tool call. The matchers that were checked and the hook exit codes are written to the log.

According to the official docs as of writing (October 2026), edits to settings.json are applied to a running session after a short delay, without a restart. However, before v2.1.257, edits to a .claude/ folder created after the session started were not detected.

When MCP server tools don't appear

Use /mcp to check the servers, their connection status, and whether they are approved in the current project. The main reasons tools don't appear even when the definition is correct are as follows.

  • Project-scoped servers in .mcp.json require a one-time approval. If you dismiss the prompt, the servers stay disabled until you approve them from /mcp.
  • If startup fails, the usual cause is a relative path in command or args. Paths are resolved from the directory where you launched Claude Code, not from the location of .mcp.json. Use full paths for local scripts.
  • If the server shows connected but has 0 tools, run /mcp and choose Reconnect. If that doesn't help, run claude --debug=mcp and read the server's stderr in the debug log.

Pay attention to where the file goes, too. Project settings go in .mcp.json at the repository root, not inside .claude/, under the mcpServers key. settings.json does not read the mcpServers key.

Isolating the problem with a clean configuration

If you can't narrow down the cause, start with claude --safe-mode. This disables CLAUDE.md, skills, plugins, hooks, MCP servers, custom commands and agents, and more, while authentication, model selection, built-in tools, and permissions work as usual. If the problem goes away, one of the disabled items is the cause. Your organization's managed hooks and settings policies still apply in safe mode.

If the problem persists, confirm whether you can reproduce it in a session that doesn't use your own settings. First, in a shell where Claude Code isn't running, create an empty directory and move into it (example for Bash or Zsh).

mkdir -p ~/claude-clean/empty && cd ~/claude-clean/empty

Next, in the same shell, point to a new config directory and start Claude Code with --setting-sources user to disable project settings. The initial setup screen appears on first launch.

CLAUDE_CONFIG_DIR=~/claude-clean/config claude --setting-sources user

Finally, try to reproduce the problem. If it goes away, the cause is in your user or project settings, so copy the files in ~/.claude.json and ~/.claude one at a time to narrow it down. If it persists, check managed settings with /status and also check the environment variables in your shell.

FAQ

Do I need to restart Claude Code after editing settings.json?

According to the official docs, changes are applied to the running session after a short delay, so no restart is needed. However, before v2.1.257, edits to a .claude/ folder created after the session started aren't detected. If /hooks still shows the old definitions after you save, run /hooks again to refresh the view.

Source: Debug your configuration

How do I check whether a setting I configured is being overridden by another setting?

Run /status to see where the active settings were loaded from and whether managed settings are present. According to the official docs, managed settings are applied first, and for everything else the nearer scope takes precedence, in the order local, project, user. Environment variables and command-line flags also act as override layers. You can check for invalid settings files with claude doctor.

Source: Debug your configuration

Why doesn't the MCP server I wrote in .mcp.json show up?

The official docs say to check that you haven't left the one-time approval dismissed, and that .mcp.json is at the repository root with entries under the mcpServers key. If a server fails to start, relative paths in command or args can also be the cause. Start by checking the status with /mcp.
