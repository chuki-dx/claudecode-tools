What Claude Code hooks are: how to write the settings and when to use them

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • hooks automatically run shell commands you define at set points in the behavior of Claude Code (the AI coding agent from Anthropic that runs in the terminal). They let you always run a given process without relying on the LLM choosing to run it.
  • You configure hooks under hooks in a settings file, specifying the event name, the matcher, and the command to run. You can check what's registered with /hooks.
  • They suit code formatting and blocking edits to protected files, but there are constraints, such as PostToolUse not being able to undo an action. Before a company-wide rollout, check the specification for the relevant event in the official docs.

What you can do with hooks

According to the official docs, hooks are shell commands that you define. Claude Code runs them at specific points in its lifecycle, so you get deterministic control: a given action always happens. Main uses are enforcing project rules, automating repetitive work, and integrating with existing tools.

The official docs give examples such as formatting files after edits, blocking commands before they run, notifying you when input is needed, and injecting context at session start.

Most hooks run a shell command with "type": "command". Other types are http, mcp_tool, prompt (a single LLM judgment), and agent (multi-turn verification with tool access). agent is experimental and may change in the future, so command hooks are recommended for production workflows.

This article is based on the official docs I referenced as of writing (October 2026). Events and settings may be updated, so check the latest content before you deploy.

How to configure it: your first hook

To create a hook, add a hooks block to your settings file. Event names are listed as keys inside a single hooks object. If a hooks key already exists, don't replace the whole thing; add your entry at the same level as the existing event keys.

Here is an example that runs Prettier (a code formatter) after a file-editing tool runs. According to the official docs, you add it to .claude/settings.json in the project root.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

PostToolUse is the event that fires after a tool call succeeds. The Edit|Write value for matcher means the hook runs only when the Edit or Write tool is used; it does not run for Bash or Read. Without a matcher, the hook runs every time that event occurs. The command uses jq (a command for processing JSON) to extract the path of the edited file and passes it to Prettier.

After setting it up, type /hooks at the prompt to open the list of hooks and confirm the registration. A successful hook shows nothing in the conversation, so verify it by its effect (here, whether the file was formatted).

Where settings files go and their scope

In the official docs, where you place a hook determines its scope.

  • ~/.claude/settings.json: All of your own projects. Limited to your machine and not shared.
  • .claude/settings.json: applies to that project only. You can commit it to the repository and share it.
  • .claude/settings.local.json: that project only. Not shared
  • Managed policy settings: Organization-wide. Controlled by administrators
  • A plugin's hooks/hooks.json, and the frontmatter of skills and subagents: these apply while the plugin is enabled, for the session after the skill is invoked, and while the subagent is running, respectively.

Hooks you want standardized across the company go in .claude/settings.json and are shared through the repository. To turn hooks off, write "disableAllHooks": true in a settings file. However, a project settings file can override your own settings, and hooks in managed settings keep running unless disableAllHooks is also set on the managed settings side.

How to think about input, output, and exit codes

When an event occurs, Claude Code passes event-specific data as JSON to the hook's standard input. For example, a PreToolUse hook receives tool_name and tool_input. Your script reads that and signals what to do next through its exit code.

  • Exit code 0: No objection. For PreToolUse it does not count as approval, and the normal permission check continues. For events such as UserPromptSubmit and SessionStart, stdout is added to Claude's context as text
  • Exit code 2: Blocks the action. Write the reason to standard error. Where the reason is delivered depends on the event, and some events, such as SessionStart, cannot be blocked
  • Anything else: The result depends on what is written to standard output, and in most cases it is handled as a non-blocking error and processing continues

The following is an example of a script that blocks a command with PreToolUse.

#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q "drop table"; then
  echo "Blocked: dropping tables is not allowed" >&2  # stderr becomes Claude's feedback
  exit 2                                               # exit 2 = block the action
fi

exit 0  # exit 0 = no decision; the normal permission flow applies

For finer control, return JSON on stdout with exit code 0. The official docs advise choosing one approach per hook, either blocking with exit code 2 or structured control with exit code 0 and JSON, and not mixing them. Also, when multiple hooks match the same event, they run in parallel, and for PreToolUse permission decisions the strictest result wins (in the order deny, defer, ask, allow). Even if one hook returns deny, the other hooks still run to completion.

When to use it and what to watch for

Where it fits best

  • Format code after edits (PostToolUse)
  • Block edits to files you want to protect, such as .env, package-lock.json, and .git/ (PreToolUse with script exit code 2). The script must be executable
  • Notification when Claude is waiting for your input (Notification). The official docs have examples for macOS, Linux, and Windows
  • Context re-injection (SessionStart with compact). It makes up for information lost when the conversation is summarized.
  • Audit log for configuration file changes (ConfigChange)

Notes

  • PostToolUse runs after the tool has already executed, so it can't undo the action.
  • A matcher of just Edit|Write won't catch cases where Claude changes files through shell commands. If you want to audit every change, the docs describe a Stop hook that inspects the working tree after each turn.
  • Filtering with the if field is best-effort. For strict allow/deny control, the docs direct you to use the permissions system rather than hooks.
  • If you auto-approve with PermissionRequest, keep the matcher narrow. Specifying .* or leaving it empty auto-approves every permission prompt, including file writes and shell commands
  • A PreToolUse deny takes effect even in bypassPermissions mode. A hook's allow, on the other hand, can't override a deny rule in settings.

FAQ

If I just want to give Claude the same background in every session, should I use hooks?

The official docs advise considering CLAUDE.md rather than a SessionStart hook if you want to load context at the start of every session. The compact matcher for SessionStart is introduced as an example for re-injecting important information after compaction.

Source: Automate actions with hooks

What should I check first when a hook doesn't run?

The official docs say to first check with /hooks that the hook appears under the correct event. The matcher must match the tool name exactly, including case. JSON in settings files can't contain trailing commas or comments. If a script doesn't run, check its execute permission. You can see detailed logs with claude --debug.

Source: Automate actions with hooks

Can I use hooks for tasks that can't be defined by rules and require judgment?

According to the official docs, a prompt hook has a Claude model make a single judgment, while an agent hook verifies using tools such as file reads. The agent hook is experimental and may change in the future, and command hooks are recommended for production.
