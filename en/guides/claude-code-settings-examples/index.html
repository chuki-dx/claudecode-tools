Claude Code settings.json examples: how to read and write the three official samples

Published: October 17, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • As of writing (October 2026), the official docs include three samples: ~/.claude/settings.json for personal use, .claude/settings.json for teams, and managed-settings.json for organizations.
  • Every sample here is meant to be copied, trimmed to the keys you need, and edited with your own values. They are not recommended baseline settings.
  • The tabs with comments are for reading; a settings file can't contain comments. Copy from the tab without comments.

Three samples: choose by where you place them

The official docs for Claude Code (an AI coding agent from Anthropic that runs in the terminal) have a page called "Example settings files" about the settings.json configuration file. It includes realistic examples for individual developers, teams, and organizations.

  • Personal: ~/.claude/settings.json
  • Team (committed to the repository): .claude/settings.json
  • Organization: managed-settings.json

According to the official docs, each example is a file that someone in that role would likely write, meant for you to look at the shape and copy the parts you need. They are not recommended baseline settings. For each key's type, default value, and where it can be set, check that key's entry in the settings reference.

Each example has two tabs. Copyable settings file is the version you can save as-is, and What each key does is the version with a comment above each key. Claude Code does not accept comments in settings files, so copy from the first tab.

Example personal ~/.claude/settings.json

The personal example picks a model and effort level, adjusts the terminal, and pre-approves one read-only command and one file read. Keys that aren't written keep their default values. If you put it in ~/.claude/settings.json, it applies to every project you open.

  • model: starts every session with claude-sonnet-5.
  • modelSettings: Sets Sonnet 5's effort to xhigh, above the default of high.
  • editorMode, theme: Use vim key bindings at the prompt and switch to a bright, color-blind-friendly theme (light-daltonized).
  • statusLine: Shows the model name and used context below the prompt.
  • cleanupPeriodDays: Deletes local data, such as session records, older than 20 days.

The permissions are as follows. They allow running git diff and reading .zshrc without asking for confirmation.

  "permissions": {
    "allow": [
      "Bash(git diff *)",
      "Read(~/.zshrc)"
    ]
  },

Example team .claude/settings.json and what to check before committing

The team example is meant to be committed to the repository so that everyone who clones it uses the same permissions, hooks, and plugin marketplaces. Put it in .claude/settings.json at the top level of the repository. For permissions, it allows Bash(npm run *), asks for Bash(git push *), and denies reading .env files and the secrets folder.

    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]

There are also examples that enable marketplace plugins with enabledPlugins. However, plugins from external sources such as GitHub repositories must be installed once by each user.

What to know before you commit

  • It also reads them in cloud sessions. A cloud session starts from a clone of the repository, so committed files apply there too.
  • Put telemetry settings in managed settings or personal settings. Claude Code ignores OpenTelemetry exporter variables written in a repository's settings file, except for a few values that turn telemetry off.
  • allow rules and extraKnownMarketplaces take effect only after each user trusts that folder itself. Trusting a parent folder is not enough. deny and ask rules apply whether or not the folder is trusted.
  • The hook in this example runs the script .claude/hooks/block-rm.sh in the repository.
  • A rule matches only when the command or path is written exactly as the rule says. Bash(git push *) does not match git -C . push. Read(./.env) alone blocks the file tools and commands that name the file, such as cat .env, but it does not block a grep -r over the whole directory. This example closes that gap with a sandbox block.

Example managed-settings.json for an organization

The organization examples show the shape of the managed keys, with one reasonable value for each key. The official docs say these are not recommended policies; they tell you to pick the keys that fit your own requirements and set your own values. Replace the sample organization UUID, server URL, and marketplace with your own.

To distribute, place the file as managed-settings.json, or deliver the same JSON through MDM (a tool for managing devices in bulk) or server-managed settings. A single distributed file applies to every machine or account it reaches. Server-managed settings don't yet support per-group policies, so to vary values by group, distribute separate files or profiles.

Some of the keys included in the example

  • forceLoginMethod, forceLoginOrgUUID: fix the login method and organization.
  • availableModels, enforceAvailableModels: Restrict the available models to opus and sonnet. With the latter set, the Default option also follows the list.
  • permissions.deny, disableBypassPermissionsMode: deny things like Bash(curl *) and turn off bypass permissions mode.
  • allowManagedPermissionRulesOnly: ignores permission rules in user, project, and local settings.
  • allowedMcpServers: Specifies MCP servers by URL rather than by name, because users can name any server github.
  • strictKnownMarketplaces: restricts plugin sources to a single marketplace.
  • requiredMinimumVersion: versions older than 2.1.150 won't start.
  • cleanupPeriodDays: Keeps local data for 7 days.
  • companyAnnouncements: Shows a message to everyone at startup.

sandbox runs the commands Claude Code executes inside a sandbox, refuses to start if the sandbox can't be set up, and doesn't allow blocked commands to be retried outside it. Network access is limited to npm and GitHub, and users cannot add domains.

  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": [
        "registry.npmjs.org",
        "github.com"
      ],
      "allowManagedDomainsOnly": true
    }
  },

FAQ

Can I write comments in settings.json?

According to the official docs, Claude Code does not accept comments in settings files. In each example, the "What each key does" tab is the commented version for reading; copy from the comment-free "Copyable settings file" tab.

Source: Example settings files

Do allow rules written in the team's settings.json take effect immediately for everyone who clones the repo?

According to the official docs, allow rules and extraKnownMarketplaces take effect only after each person trusts that folder itself. Trusting a parent folder is not enough. Deny and ask rules apply regardless of whether the folder is trusted.

Source: Example settings files

Can I roll out the organization sample company-wide as is?

The official docs say these are not recommended policies. Choose the keys that fit your own requirements and set the values yourself. Replace the organization UUID, server URL, and marketplace with your own. If you want different values per group, distribute a separate file or profile to that group.
