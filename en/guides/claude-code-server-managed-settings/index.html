How to distribute Claude Code settings from the admin console (server-managed settings)

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • With a Claude for Teams or Claude for Enterprise plan, you can roll out Claude Code (Anthropic's AI coding agent that runs in the terminal) settings to the whole organization from the admin console.
  • This method suits organizations without MDM (a system for managing devices in bulk) and users on unmanaged devices. However, it is client-side control, not a security boundary.
  • Settings apply uniformly to everyone; per-group settings are not supported. Settings may not reach users who use Console API keys or third-party provider configurations.

What it does: distribute settings from Anthropic's servers

According to the official docs, server-managed settings deliver Claude Code settings from Anthropic's servers. The client fetches settings from the server at startup and refreshes them every hour during a session.

Settings available in settings.json are supported, except those limited to OS-level policy delivery. This includes hooks (a mechanism for running commands at specific points), environment variables, and admin-only settings such as allowManagedPermissionRulesOnly.

The following conditions are required to use it.

  • A Claude for Teams or Claude for Enterprise plan
  • The Owner or Primary Owner role in your Claude organization is required to view and edit the settings
  • Network access to api.anthropic.com

If a Team or Enterprise organization shows an "no access" message on the screen, ask an Owner or Primary Owner to make the change. Because changes to these settings apply to every user in the organization, the official docs ask that you limit who can change them to trusted administrators.

Source: Configure server-managed settings

Choosing between server management and endpoint management

The official docs list two methods of centralized management. Server-managed settings are delivered from Anthropic's servers. Endpoint-managed settings are distributed directly to devices through OS policies (managed preferences on macOS, the registry on Windows) or managed settings files.

  • server-managed settings: Suited to organizations without MDM, or to users on unmanaged devices
  • endpoint-managed settings: suited to organizations with MDM or endpoint management

If devices are already enrolled in MDM or similar, endpoint-managed settings give a stronger guarantee, because the settings file can be protected from user changes at the OS level.

However, endpoint-managed settings don't reach cloud sessions in Anthropic-hosted environments. Organizations whose developers use cloud sessions are advised to also configure server-managed settings. Sessions in self-hosted environments also read the managed settings file inside the runner image. To see which one applies and when, check settings precedence in the official docs.

Source: Configure server-managed settings

Setup steps: write the JSON in the admin console and save it

  1. In the claude.ai console, open Organization settings > Claude Code > Managed settings
  2. Writing settings in JSON
  3. Save

The example in the official docs enforces the permission deny list, prohibits bypassing permissions, and restricts permission rules to only those defined in managed settings.

{
  "permissions": {
    "deny": [
      "Bash(curl *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true
}

Note that a Bash(curl *) rule matches curl exactly as Claude writes it. It does not match /usr/bin/curl or sh -c 'curl …'. For network restrictions that don't rely on the command string, the docs describe using the sandbox block and allowManagedDomainsOnly. Check the official docs for details.

Hooks can be written in the same format as settings.json. Because hooks run shell commands, interactive sessions show a security approval dialog before they are applied.

After you save, clients pick up the new settings at their next startup or in the hourly fetch. The editor validates the content against the Claude Code settings JSON schema, and if there are problems it shows a warning and changes the button label: Update with errors if the settings are already saved, or Add with errors if not. You can save even with warnings.

The schema can lag behind the latest release, so keys that appear in the settings reference may trigger warnings. Claude Code runs its own validation after it receives the file.

How to verify delivery

According to the official docs, you can check as follows.

  • Ask users to restart Claude Code. If the settings include ones that trigger an approval dialog, the dialog shows the contents the next time they are fetched
  • Ask the user to run /permissions and check the permission rules in effect
  • To see what a specific device received, ask the user to run claude doctor and read the Managed settings (remote) line (Claude Code v2.1.248 or later)

This line shows one of the following: settings loaded successfully, no settings configured for your organization, a fetch failure (with the cause and whether a cache exists), or a skipped fetch (with the reason). In a running session, you can also check the same line with /status, for example after a fetch failure.

Limits and caveats: know in advance when it won't reach

Current limitations

  • Settings apply uniformly to all users in the organization. In the official docs as of writing (October 2026), per-group settings are not supported.
  • You can't distribute managed-mcp.json. Distribute allowedMcpServers and deniedMcpServers instead
  • Settings limited to OS-level policy, such as policyHelper and wslInheritsWindowsSettings, have no effect here. Distribute them through MDM or the system managed-settings.json

Conditions under which it is not delivered

Delivery requires a direct connection to api.anthropic.com. Supported authentication includes Team or Enterprise OAuth login, CLAUDE_CODE_OAUTH_TOKEN, and an API key you set directly. Keys returned by apiKeyHelper and Workload Identity Federation credentials are not retrieved.

An API key from the Console belongs to a different organization than your claude.ai organization. As a result, CI jobs that authenticate with that key don't receive the settings from the admin console. The fetch is also skipped if you set a CLAUDE_CODE_USE_* variable or a non-default ANTHROPIC_BASE_URL in the shell. It is also not fetched in Cowork sessions in Claude Desktop.

Security positioning

The official docs describe server-managed settings as "a client-side control, not a security boundary." On unmanaged devices, users can bypass them even without admin rights. Older versions of Claude Code don't fetch the settings, a cache is used when the API is unavailable, and if there is no cache the settings are not applied. If you need a strong guarantee, use endpoint-managed settings on MDM-enrolled devices. Audit logs of settings changes require contacting your Anthropic account team.

FAQ

Can I distribute different settings to different groups?

According to the official docs, settings apply uniformly to all users in the organization, and per-group settings are not yet supported.

Source: Configure server-managed settings

How do I check whether the settings have reached a device?

Have users restart Claude Code, then check the effective permission rules with /permissions. You can confirm the settings were fetched on the Managed settings (remote) line of claude doctor. Claude Code v2.1.248 or later is required.

Source: Configure server-managed settings

Do admin console settings also apply to CI jobs that run on a Console API key?

It won't work, because a Console API key belongs to a different organization. The official docs list two options: using an OAuth token created with claude setup-token, or using endpoint-managed settings. OAuth tokens can't be used in jobs that run with --bare.
