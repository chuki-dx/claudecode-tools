How to write Claude Code permission rules: Bash and Read patterns and allow/deny precedence

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • Permission rules are written as Tool or Tool(specifier). A tool name alone matches every use of that tool; adding a specifier in parentheses narrows it down.
  • In Bash rules, put * after the subcommand. Bash(git log *) matches only git log, while Bash(git *) matches every git command.
  • deny wins over allow at every level. A project's allow does not apply until you accept the workspace trust dialog.

Basic form of a permission rule: tool name and specifier

According to the official docs as of writing (October 2026), permission rules are written in the form Tool or Tool(specifier). Parentheses inside a specifier are treated as literal characters, so commands and paths that contain parentheses need no escaping. You use this format to specify what Claude Code (Anthropic's AI coding agent that runs in the terminal) is allowed or denied.

Whole tools and narrowing down with specifiers

  • Writing only a tool name, such as Bash, WebFetch, or Read, matches every Bash command, every web fetch request, and every file read, respectively
  • Bash(npm run build) matches the exact command npm run build
  • Read(./.env) matches reads of the .env file in the current directory
  • WebFetch(domain:example.com) matches fetch requests to example.com

Bash(*) means the same as Bash. For a deny rule, either form removes that tool from Claude's context. Also, a tool's display label can differ from its official name (for example, the official name of Stop Task is TaskStop), and rules do not match the display label. Check the official tool reference for the exact names.

Wildcards in Bash rules: where you put the * matters

In a Bash rule, * matches any string including spaces, and a rule without * matches exactly that one command. The official docs warn you to put * after the subcommand. Everything before the first * is matched as written, so Bash(git log *) allows only git log, while Bash(git *) allows every git command. An allow rule that puts * before the subcommand, like Bash(git * main), triggers a warning at startup.

With the following settings, npm scripts and git commit run without confirmation, and commands starting with git push are denied. However, a push written differently, such as git -C . push, does not match. Check the official docs for details.

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}

Matching examples

  • Bash(npm run *) matches npm run build and npm run, but not npm install
  • Bash(ls *) matches ls -la and ls, but not lsof. Bash(ls*) also matches lsof.
  • Bash(* --help *) matches npm --help x, but does not match npm --help

A trailing space plus * also matches the bare command only when that * is the only wildcard in the rule. The space before the trailing * is part of the rule. :* is an equivalent way to write a trailing wildcard, so Bash(ls:*) means the same as Bash(ls *), but it is recognized only at the end of a pattern. In Bash(git:* push), the colon is treated as a literal character, so it does not match git commands.

Parameter matching and tool-name wildcards

deny and ask rules can match top-level input parameters of built-in tools with Tool(param:value). allow rules continue to use each tool's own specifier syntax, as before.

  • Agent(model:opus) matches Agent calls that request the Opus model tier
  • Bash(run_in_background:true) matches Bash calls that run in the background
  • One rule can specify only one parameter. To use multiple conditions, write two rules
  • A * in the value matches any string; without a *, the value must match exactly

Primary content fields such as Bash's command or Read's file_path cannot be specified this way. Bash(command:rm *) can be bypassed with compound commands, so Claude Code ignores it and shows a warning at startup. Use Bash(rm *), Read(./path), or WebFetch(domain:host) instead.

deny and ask rules can also use glob patterns in the tool name position. "*" matches all tools, and "mcp__*" matches MCP tools from all servers. The following setting denies all MCP tools.

{
  "permissions": {
    "deny": [
      "mcp__*"
    ]
  }
}

In allow rules, a glob can only go after the literal mcp__ and the server name. mcp__puppeteer__* matches all tools on the puppeteer server. An allow rule whose beginning isn't fixed, such as "*" or "mcp__*", is skipped and auto-approves nothing. To narrow by MCP tool parameters, pass a deny rule with --disallowedTools.

Precedence of allow and deny

According to the official docs, permission rules follow the same precedence as other settings, with managed settings at the top. No other level, including command-line arguments, can override managed permission rules.

A tool denied at any one level cannot be allowed at another. For example, a managed deny cannot be overridden by --allowedTools, while --disallowedTools can add restrictions beyond what managed settings define. If user settings allow a tool and project settings deny it, the deny wins, and conversely a user deny stops a project allow. This is because a deny in any scope is evaluated before any allow. If you need a prohibition to hold reliably, write it as a deny. For how to distribute managed settings, check the official docs.

A project's allow rules take effect after the trust dialog

permissions.allow and permissions.additionalDirectories in .claude/settings.json are settings that widen permissions. According to the official docs, they apply only after you accept the workspace trust dialog for that folder. The dialog lists the rules and directories that the folder grants. deny and ask only restrict, so they are not affected.

  • Inside a repository: trust is recorded per git repository root. Nested repositories such as submodules are not covered
  • Outside a repository: trust applies per the directory where you launched it
  • Launching from your home directory: trust is kept only for that session and is not written to disk

The dialog appears only in interactive sessions. With claude -p or the SDK it isn't shown, the project's allow rules aren't used, and a warning goes to stderr. Before running claude -p in a repository you don't trust, you can limit what gets loaded with --setting-sources user or --bare. For rules you want to apply to every project, write them in the user settings at ~/.claude/settings.json.

FAQ

What is the difference between Bash(git *) and Bash(git log *)?

Bash(git log *) allows only git log, while Bash(git *) allows every git command. An allow rule with * before the subcommand triggers a warning at startup.

Source: Configure permissions

What happens if I set allow in user settings and deny in project settings?

deny takes effect. According to the official docs, a deny at any scope is evaluated before allow, and anything denied at one level cannot be allowed at another.

Source: Configure permissions

Can I deny rm with Bash(command:rm *)?

No. Because it can be bypassed with compound commands, Claude Code ignores this rule and shows a warning at startup. Write it in the form Bash(rm *).
