No-code vs. Claude Code: 3 criteria to check before building an internal tool

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • For small internal business tools, three questions decide between no-code and code written with Claude Code (an AI coding agent that runs in the terminal): who will fix it after it's built, where the data lives, and how much it will change.
  • If the person on the front line fixes it, or it can be handled entirely within Microsoft 365 or a SaaS tool, go no-code. If it spans multiple systems or has many exceptions, code is a better fit.
  • "AI can write it, so make everything code" just moves the key-person dependency over to corporate IT. Use no-code for the parts that business users touch and code for the heavy back-end processing, and when in doubt, first decide who will fix it a year from now.

The short answer: sort it out with three questions

This article organizes the decision criteria described in the Chuki DX Lab article "Build It No-Code, or Write Code with Claude Code?" It is based on what was publicly available as of writing (October 2026), and presents the criteria the author uses for their own decisions.

An article from Chuki DX Lab says that since AI made it possible to write code, the question of whether to build with no-code or with code has actually become harder. "You can build anything in code just by asking AI," but the people who struggle after it is built are you and your team.

The article lists the following three questions.

  1. Who fixes it after it's built
  2. Where the data lives
  3. How much it changes

Use the following as a rule of thumb for sorting work into these three.

  • Staff on the front line fix it → no-code
  • Work that stays within Microsoft 365 or a SaaS product → no-code
  • Spans multiple systems or has many exceptions → code (Claude Code)

Here, no-code means building a process flow on screen, as in Power Automate.

Source: No-code or code with Claude Code? Three criteria for deciding how to build internal tools (Japanese)

Criterion 1: Who fixes it after it's built

The Chuki DX Lab article treats this as the most important criterion. If the person on the front line will fix it themselves, no-code is the better fit. They can see the flow on screen, so small changes like "change the approver" or "add a notification recipient" can be done without going through corporate IT.

On the other hand, if corporate IT will maintain it, code is also fine. The idea is that if you have Claude Code read the code, it can explain what to fix even when the person who built it is gone.

Conversely, if you build a tool in code that you intend to hand over to the people on the front line, corporate IT gets a request for every small change. The key is to choose based not on how fast you can build it, but on whether the people who will fix it can actually reach it. Before you roll it out company-wide, decide who will own fixes; that keeps your choice of tool from wavering.

Source: No-code or code with Claude Code? Three criteria for deciding how to build internal tools (Japanese)

Criterion 2: Where the data lives

If everything stays within Microsoft 365 or SaaS, no-code is easier, as the explanation goes. With Power Automate, connections to Outlook, Teams, SharePoint, and so on (connectors) are ready out of the box, so you rarely struggle with authentication setup.

Code suits cases that span internal file servers or multiple systems. For example, a task like "compare a CSV exported from the core system with an Excel ledger and list only the differences" can be built with no-code tools, but the screens get more complex as conditions grow. With code, you can write the conversion and matching rules in detail.

If you work in corporate IT, check first where the relevant business data is normally stored, which makes this criterion easier to apply.

Source: No-code or code with Claude Code? Three criteria for deciding how to build internal tools (Japanese)

Criterion 3: how much it changes

If the steps are nearly fixed, no-code is enough, the docs say. If you just send the same kind of data to the same place every month, you can build it once and be done.

If conditions and exceptions keep growing every month, choose code. With no-code tools, the whole flow tends to become hard to follow on screen as branches multiply. With code, you can keep a history of what changed and why, so you can later check when and why a condition was added.

The idea is that the more changes a task involves, the more it matters whether you can trace what happened afterward.

Source: No-code or code with Claude Code? Three criteria for deciding how to build internal tools (Japanese)

A common mistake: "AI can write it, so make everything code"

What the Chuki DX Lab article warns against in particular is "building everything in code because AI can write code." It explains that doing so leaves only corporate IT able to fix things, so the dependence on a single person (a state where only specific people can fix it) simply shifts from "the person who wrote the macro" to "corporate IT."

The author says the following way of splitting things up has worked best for them so far.

  • Use no-code for the parts that staff touch (input forms, approvals, notifications)
  • Heavy back-end processing (aggregation, matching, conversion) goes to code

If you are still undecided, the advice is to first decide who will fix it a year from now, then choose. Once that person is settled, criteria 2 and 3 can be considered in light of the tools they are best at.

Notes before you read

The criteria introduced here are simply an approach based on one IT admin's experience. The article does not cover costs, licensing, security settings, or specific ways to use Claude Code. When you apply this to your own environment, check each product's official docs.

What to check before trying it: lessons from a part-time in-house SE

In another Chuki DX Lab article (a retrospective by a part-time in-house IT admin), the author writes that internal DX stumbles tended to come from the order of steps and how responsibilities were assigned, more than from tool performance. The following points are useful both before and after you decide between no-code and code.

Don't choose the tool first

The article gives an example where the product was chosen first and applied to the work afterward, so the tool's assumptions didn't match the actual workflow and data entry became more work. As a next step, it describes asking people on the floor "what is the current procedure, who does it, and what is difficult" before choosing a tool, and writing the answers on a single sheet of paper.

Checklist before and after you build it

The author of that article checks the following before trying a new mechanism.

  • Have you seen the current procedure on the floor with your own eyes?
  • Who is struggling, and what has to decrease for you to call it a success
  • Who does what first when you're not available
  • Is it small enough to try in one department or one workflow?
  • Have you decided when to stop?

You don't need to satisfy every item before you start, but simply knowing which ones are missing is said to make recovery faster when you get stuck. Criterion 1, "who fixes it," also overlaps with "who does what first when you're not there."

It also says that when trying Claude Code, the order is to start by using it only for your own work and set the rules before expanding it company-wide.

FAQ

What problems come up when you build tools in code for people on the front line?

A Chuki DX Lab article explains that every small change ends up as a request to corporate IT. For that reason, it says the key is to choose based on whether the people who will maintain it can actually reach it, rather than on how fast it is to build.

Source: No-code or code with Claude Code? Three criteria for deciding how to build internal tools (Japanese)

Why is code a better fit for tasks with many branches and exceptions?

This is because with no-code tools, it tends to get hard to follow the whole flow on screen as branches multiply. With code, you can keep the changed locations and reasons as history, so the article explains that you can later check when and why a condition was added.

Source: No-code or code with Claude Code? Three criteria for deciding how to build internal tools (Japanese)

In what order should I proceed when rolling out Claude Code across the company?

A retrospective by a part-time in-house SE says they first used it only for their own work and set rules before spreading it across the company. For the rollout, the approach described is to try it small first, in one department and one task, record the benefit and the effort, and then decide whether to expand. The source doesn't describe the specific content of the rules, so check the official docs or other references.
