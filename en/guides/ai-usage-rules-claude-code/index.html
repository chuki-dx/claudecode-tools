How to think about generative AI usage rules before using Claude Code at a small or midsize company

Published: October 15, 2026 · Chuki DX Lab · The content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section.

Key takeaways

  • Before you start, decide five things: what Claude may do without asking for confirmation, how to treat external text, where to keep secrets, how data is handled, and how to share settings.
  • To check whether your data will be used for training, look at three layers separately: the terms (your contract plan), the data you bring in, and the tool settings.
  • According to the official docs, individual plans let you choose in settings whether your data is used for training, while business plans are, as a rule, not used for training under the commercial terms. There are conditions, though, and the terms change, so check the latest version when you adopt it.

Decide this first: think of rules in three layers

Claude Code (an AI coding agent from Anthropic that runs in the terminal) is an AI agent that can read and write files and run commands on its own. Because it can do more than a chat-based AI, there are more things to decide before you use it.

A Chuki DX Lab article explains that "not training on your data" can't be settled with a single setting, and breaks it down into the following three layers.

  1. Terms (contract) layer: Decide which plan and account to use, then check how data is handled on the official pages and record it.
  2. Data layer: decide what not to put in folders Claude Code can read in the first place.
  3. Settings layer: use settings to make files you don't want read unreadable, and document the usage rules.

You can't change the terms yourself, but you can decide your own data and settings. If you design things so that confidential information is never handed over in the first place, the damage stays limited even if the terms change. The same article also says that a blanket ban tends to lead to shadow AI (AI use the company doesn't know about). What to let it do without confirmation, and how to handle external text

According to a Chuki DX Lab article, Claude Code lets you choose with a permission mode how much it can do without asking, and you can also set allow and deny rules for individual commands. For example, a command like curl, which fetches content from the web, is not automatically allowed by default.

The article suggests that corporate IT draw the line in the following three categories. All are examples.

  • Operations to allow automatically (e.g., reading files, running tests)
  • Actions to confirm every time (for example: deleting files, communicating externally)
  • Prohibited actions (e.g., connecting to production servers, sending files outside the company)

It also warns that automating everything because it is convenient leaves no place to stop the AI when it does something wrong.

Another thing to watch for is prompt injection. This is an attack where text like "follow this instruction" is planted in a web page, an email, or a file from outside, and the AI mistakes it for a real instruction and acts on it. The official docs reportedly list points such as reviewing suggested commands before running them, not feeding untrusted content directly to the AI, and reviewing changes to important files before accepting them.

As an internal rule, the suggestion is to require a person to check before running anything when Claude Code reads a client's files or text copied from the web, rather than accepting its suggestions at face value.

Where to keep secrets, and sharing settings across the team

AI agents read files in the working folder, so any passwords or API keys stored there may be read during a task. The article lists the following countermeasures.

  • Collect them in a dedicated configuration file (for example, .env)
  • Keep that file out of version control (add it to .gitignore)
  • Don't write keys directly in code, notes, or procedure documents
  • Don't paste the key itself into requests to AI, either

Also, if settings are left to individuals, they end up inconsistent: "A allows everything automatically" while "B confirms every time." Claude Code has settings that an organization can enforce (managed settings) and a way to share per-project permission settings as files. The official docs reportedly also recommend sharing approved permission settings through version control and reviewing them regularly. At a minimum, I suggest starting by creating one standard permissions file and distributing it to everyone's environment.

How conversation data is handled by plan

The official docs explain the training policy separately for each plan.

  • Individual plans (Free, Pro, Max): Users can choose whether their data is used to improve future models. When the setting is on, Claude Code data from these accounts is also used for training.
  • For business use (Team, Enterprise, API, third-party platforms, Claude Gov): under the commercial terms, code and prompts sent to Claude Code are not used to train generative models. The exception is when the customer chooses to provide data for model improvement (for example, the Development Partner Program).

The Development Partner Program is something an organization's admin must explicitly opt in to. It covers only Anthropic's own API; the docs state that users of Amazon Bedrock or Google Cloud's Agent Platform are excluded.

Retention periods differ too. For individual plans, it is 5 years if you allow model improvement and 30 days if you don't. The standard for business plans (Team, Enterprise, API) is 30 days. Zero data retention (ZDR) is available for Claude Code on Claude for Enterprise, for accounts that meet the requirements. It is not included in the standard Enterprise plan and is enabled per organization after confirmation.

If you start with an individual plan, a Chuki DX Lab article suggests checking the settings at setup and keeping screenshots as a record. Decide first which plan you will use, then confirm it on the official page and record it.

Notes on feedback, surveys, and local storage

Separately from the training policy, the official docs also explain how the information users send and the information stored locally are handled.

  • Conversation records shared with /feedback are retained for 5 years, including /bug and /share, which are reported through the same path.
  • For the session quality survey rating itself, only the rating is recorded. A follow-up question may then ask whether Anthropic may view the session transcript, and the conversation transcript and related data are uploaded only if you choose "Yes" (for sessions on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, and the signed-in Claude apps gateway, nothing is uploaded; it is written to a local archive in ~/.claude/feedback-bundles/ and does not leave your machine until you transfer that file). Known API key and token patterns are redacted, but source code and file contents are sent as-is, and shared transcripts are retained for up to 6 months.
  • To disable the survey, set CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY=1.
  • Session transcripts are also stored locally in plain text, kept in ~/.claude/projects/ for 30 days by default. You can adjust the period with cleanupPeriodDays.

For details, the docs direct you to the commercial terms, consumer terms of use, and privacy policy. Before you roll this out company-wide, check the official docs for the content that matches the plan you use.

FAQ

How does the handling of training differ between individual plans and business plans?

According to the official docs, on Free, Pro, and Max, users choose this in their settings, and when it is on, Claude Code data is also used for training. On Team, Enterprise, the API, and similar plans, data is generally not used for training under the commercial terms. The exception is when a customer chooses to provide data to improve the models.

Source: Data usage

Is banning generative AI entirely the safe choice?

A Chuki DX Lab article says that a total ban may look the safest, but it tends to invite shadow AI, where people use AI secretly on personal phones and accounts. It argues for a design you can explain as "check in this order, and use only within this scope."

Source: Design Patterns for Keeping Claude Code from Learning Your Business Information — 5 Rules Corporate IT Should Decide Before Rollout (Japanese)

How should I handle API keys and passwords?

In Chuki DX Lab's article, the recommendation is to put keys in a dedicated config file such as .env, and list it in .gitignore so it stays out of version control. Don't write the key itself in code, notes, runbooks, or prompts to the AI.
