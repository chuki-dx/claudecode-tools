What the Claude Code sandbox is: what it can restrict, organization settings, and limits

Published: October 24, 2026 ・ Chuki DX Lab ・ Content is based on the official docs and other sources as of writing (October 2026); sources are listed at the end of each section

Key takeaways

  • The sandbox is off by default. Enable it by running /sandbox or setting sandbox.enabled to true. It applies to shell commands that Claude runs and their child processes.
  • Built-in tools such as Read and WebFetch, hooks, and local MCP servers are not covered. If your organization needs to require it, distribute the sandbox key through managed settings.
  • The official docs state that the sandbox is not a complete isolation boundary. This reflects the content as of writing (October 2026), so check the latest official docs before adopting it.

What the sandbox restricts (defaults)

According to the official docs, the sandbox in Claude Code (Anthropic's AI coding agent that runs in the terminal) runs the shell commands Claude executes, and the processes they start, inside a boundary. To enable it, run /sandbox in a session, or set sandbox.enabled to true in a settings file such as ~/.claude/settings.json.

The default reach of commands inside the sandbox is as follows.

  • Write access: the working directory, a per-user temporary directory, and any directories you added. Protected paths remain write-denied. You adjust this with filesystem.allowWrite and filesystem.denyWrite.
  • Read: most of the machine is readable, including credential files such as ~/.ssh and ~/.aws/credentials. You adjust this with filesystem.denyRead and credentials.
  • Network: There is no direct outbound path. A proxy on the machine checks requests against the allowed domains (initially empty). How hosts outside the allowed list are handled depends on the permission mode. You adjust this with network.allowedDomains and network.deniedDomains.
  • Environment variables: inherited from Claude Code, including any secrets in the environment. You adjust this with credentials and CLAUDE_CODE_SUBPROCESS_ENV_SCRUB.

What runs outside the sandbox

According to the official docs, the sandbox wraps shell commands. The following run outside it.

  • Built-in tools such as Read, Edit, Write, WebFetch, and WebSearch follow the permission rules. denyRead does not block the Read tool, and allowedDomains does not restrict WebFetch.
  • Command-type hooks, local MCP servers, plugin monitors, LSP servers, status line commands, apiKeyHelper, and similar: these run with the user's full access.
  • Depending on your settings, shell commands also run outside the sandbox: commands you type yourself in ! shell mode (in most sessions), commands that match excludedCommands, and unsandboxed retries that Claude requests (usually after a failure inside the sandbox).

If you want all of these inside a single boundary, run the Claude Code process itself in a container, virtual machine, or sandbox runtime.

Relationship to permission rules and permission modes

The official docs describe sandboxing, permission rules, and permission modes as complementary layers. Permission rules control which tools can be used and are evaluated before execution. The sandbox works at the OS level and restricts the filesystem and network for Bash, PowerShell, and Monitor tool commands and their child processes.

Permission decisions are based on the command string (and, in auto mode, the classifier's judgment), but the sandbox boundary is enforced by the OS on the running process. So it holds no matter what the model chooses, and even if an allowed command does more than its name suggests. Paths and domains from sandbox settings and permission rules are merged into the final configuration.

/sandbox is not a permission mode. In auto-allow mode, the sandbox boundary itself takes the place of the confirmation prompt. --dangerously-skip-permissions has no such substitute, and it also skips the protected-path checks.

Settings that require the sandbox across an organization

According to the official docs, admins distribute the sandbox keys as managed settings, either in a file managed through MDM or in server-managed settings on claude.ai. The following settings enable the sandbox, prevent Claude Code from starting in unsupported environments or when dependencies are missing, and prohibit retrying outside the sandbox.

{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false
  }
}
  • failIfUnavailable: If a dependency such as bubblewrap on Linux is missing, Claude Code refuses to start instead of running unsandboxed.
  • allowUnsandboxedCommands: false: dangerouslyDisableSandbox is ignored, so a command that fails in the sandbox cannot be retried outside it.

Also consider excludedCommands for organization-approved tools, and sandbox.credentials for paths such as ~/.aws and ~/.ssh, because the default read access allows credentials. With this setting, repository settings can no longer move commands outside the sandbox (admin-required), so put the excludedCommands, allowWrite, and socket entries that approved tools need in managed settings. Requires v2.1.285 or later.

Also watch how developers can loosen things on their side. Boolean values follow managed settings, but arrays such as allowRead are merged across scopes, so developers can append entries. You can pin them to managed-only with allowManagedReadPathsOnly or allowManagedDomainsOnly.

The sandbox doesn't run on native Windows, and if you set failIfUnavailable, Claude Code exits at startup. The documented options are to roll it out only to macOS and Linux (server-managed settings apply to all users in the organization) or to move to WSL2 or a container. Also note that commands developers type in the ! shell mode run outside the sandbox in most sessions.

Limitations and caveats

The official docs state that the sandbox reduces risk but is not a complete isolation boundary. The main points are as follows.

  • Network: The default proxy neither terminates nor inspects TLS. Allowing a broad domain such as github.com can become a path for data exfiltration. If you need strong guarantees, use a custom proxy that inspects TLS.
  • Unix sockets: If you allow /var/run/docker.sock with allowUnixSockets, that effectively grants access to the host.
  • Writes: broad write permission to directories holding executables on $PATH, or to .bashrc and .zshrc, can lead to privilege escalation.
  • Settings that weaken isolation: enableWeakerNestedSandbox greatly reduces security and should be used only when other isolation is in place. allowAppleEvents and allowNestedUserNamespaces also remove isolation.
  • Not covered: Computer use runs on your actual desktop. Subagents use the same settings as the parent session.

It also says both filesystem and network isolation are required. Check that exceptions such as allowWrite, a broad allowedDomains, or excludedCommands don't cancel out the restriction on the other side.

FAQ

Is the sandbox enabled from the start?

According to the official docs, it is off by default. Enable it by running /sandbox or by setting sandbox.enabled to true.

Source: Configure the sandboxed Bash tool

If I enable the sandbox, are the Read tool and WebFetch also restricted?

No. These follow the permission rules. According to the official docs, denyRead does not block the Read tool, and allowedDomains does not restrict WebFetch.

Source: Configure the sandboxed Bash tool

Can I require the sandbox on Windows machines too?

The sandbox doesn't run on native Windows, and if you set failIfUnavailable, Claude Code exits at startup. The official docs describe running it under WSL2 or in a container.
